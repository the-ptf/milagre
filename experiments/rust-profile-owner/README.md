# Rust profile owner (checkpoint 1: reads and lifecycle)

`profile-owner` owns one Milagre data directory the way the Node daemon does, behind the same socket and client API, for **isolated copies only**. It takes the data directory's `runtime.lock` in Node's format, binds the socket Node derives for it, and answers the reads a desktop needs to show Projects and Chats, in Node's shapes. A frontend adopts it with `InstalledOwner::adopt_profile(data_dir)` (`experiments/rust-daemon-client`, feature `installed-owner`) with no client or UI change. It sends nothing, runs no provider and saves nothing: Chat sends, providers, settings, Links and remote services are later checkpoints.

```sh
profile-owner serve --data-dir D --app-version V [--chats-home H] [--worktree-root W] [--cwd C]
```

The arguments are `apps/daemon/src/cli.cjs serve`'s (`--name value` or `--name=value`). The first stdout line is Node's: `{"status":"ready","pid":…,"dataDir":<as passed>,"socketPath":…}`. It stops on `daemon:stop`, at the end of stdin (keep stdin open while it should run), on SIGTERM and on SIGINT.

## Isolation, authority and safety

- **One isolated copy.** D must be strictly inside a folder holding `MILAGRE-ISOLATED-COPY` (`milagre-owner-store`'s `Isolation`, made with `Isolation::create` or `milagre-owner-store prepare-copy`); the nearest such ancestor is opened with `Isolation::open`. The chats home and the Worktree root must be inside the same copy, and so must every Project it opens and every saved path it reads (`project:known` and `project:recent` leave others out). Node's defaults (`~/.milagre/chats`, `~/.milagre/worktrees`) are never inside a copy, so pass both.
- **Refusals kept.** `Isolation::open` refuses a copy that is inside or contains Milagre's own folders (`~/Library/Application Support/Milagre`, `~/.config/Milagre`, `~/.milagre`, `$MILAGRE_DATA_DIR`) or a Project or Link the installed Milagre registered or opened, and a copy where any Project holds a `.milagre/runtime.lock`. `owner_policy` adds the same folders under the account's home from the password database, so a `HOME` pointed elsewhere doesn't hide the real profile. Every check runs before anything is written; there is no path that opens a non-isolated profile.
- **Data dir lock exactly as Node.** `realpath(D)/runtime.lock` is taken with `RustOwnerLock` (`ownership.cjs` format: a 0700 folder, a 0600 `owner.json` written exclusively, `JSON.stringify(owner, null, 2)`, `processStartedAt` that Node's `staleOwner` reads as live), so a Node daemon and this owner exclude each other on D. A lock already there is refused whether live, stale or abandoned (Node takes the last two over); removing a dead owner's lock stays an operator's decision. The registry reads and every command check the lock is still ours.
- **Project and repository locks as Node's `ownProject`.** A Project is opened on its first `project:read`: for a Git Project `<common git dir>/milagre-runtime.lock` first, then `<project>/.milagre/runtime.lock` (through `ProjectStates`), released at stop.
- **Socket.** `milagre-owner-wire`'s `DataDirEndpoint` + `Server::bind_data_dir`: `/tmp/milagre-<uid>/<sha256(realpath D)[..24]>.sock`, the folder 0700 (made if missing, never chmodded), the socket 0600. A socket file left there is removed only while the lock proves D is ours and only when it is a socket owned by this user; anything else is refused and left.
- **Never** connects to, stops or writes the installed Node daemon or the real profile, and never takes over a lock.

What it writes, all removed at stop: D's `runtime.lock`, each opened Project's `.milagre/runtime.lock`, each Git repository's `milagre-runtime.lock`, the socket (and `/tmp/milagre-<uid>` if it was missing). Opening a Project whose saved state still holds long inline step details writes the detail sidecars Node's `readProjectState` writes on its read (content-addressed files under `.milagre/details`); a state Node saved has none to write. Nothing else: no state, chats.db row, registry or setting is saved.

## What it serves

`daemon:status` is Node's shape: `pid, version (= --app-version), protocolVersion: 1, dataDir (real path), socketPath, closing, capabilities, methods`. Capabilities are only `snapshot-pages-v1` and `result-pages-v1` (no `desktop-commands-v1`). `methods` is exactly what it serves:

| Method                                                                      | Node source it mirrors                                                                                                                   |
| --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `project:known`                                                             | registry `list()` → `{path, name, openedAt}`, Chats home left out, newest opened first, `withOrigins`                                    |
| `project:recent`                                                            | `recentProjects().list()` + `withHidden` (`project-settings.json`) + `withOrigins`, Chats home left out                                  |
| `project:read [path]`, `[path, {state:true}]`                               | `readProject` of a recent Project: opens it, `{path, name, git, version, epoch, state}`                                                  |
| `project:read [path, {state:false}]`                                        | server.cjs: `{path, name, git, version, epoch}`                                                                                          |
| `project:snapshot`, `state:read`                                            | an open Project's `{path, name, git, version, epoch, state}`; "Open the project before reading its snapshot." otherwise                  |
| `chat:messages`                                                             | an open Project's Chat page; a recent Project nobody opened is read from its chats.db without opening it                                 |
| `chat:message`                                                              | one message of an open Project with its step details read back from their sidecar                                                        |
| `chat:runs`                                                                 | `{runs: {}, seq: 0}` (nothing runs here)                                                                                                 |
| `daemon:snapshot` (paged with `daemon:snapshot-page`), `daemon:result-page` | `runtime.snapshot()`: `{links: [], projects: [{path, name, state}…], runs, ports: {}, eventSeq}`, Projects in the order they were opened |
| `daemon:focus`, `chat:set-open`, `daemon:stop`                              | the wire's view tracking and stop                                                                                                        |

Every state answered is the Project's saved state as Node holds it in memory: matched with the Worktrees found now (`reconcile.rs`, a port of `project-state.cjs` reconcileState, which Node's `ProjectStates.read` applies and saves only with a later change), Chat summaries current (`withChatSummaries`), every message included (`wholeState`), JSON written as `JSON.stringify` writes it, in Node's key order (checked on every state the test reads; a Chat saved without a summary gets it last, after the fields reconcile adds, as Node's order is). Worktrees are discovered with `milagre-registry`'s `identify` (Git's Worktree list for a Git Project, the folder itself outside Git) on every `project:read`, as `readProject` does. Anything else answers Node's unknown-command error (`{code: "COMMAND_FAILED", message: "Unknown command: <method>"}`) and is not listed.

## Known differences from Node

- **No first-load side effects.** Node's first `readProject` also marks running subagents disconnected, asks again for unknown permission modes and migrates images (changes it saves), resumes Chats a quit stopped and continues queued messages (providers), names Chats with `titlePending`, sweeps Routine run Chats, recovers handoffs, closes stale suggestion cards and refreshes diff stats; `withWorktreeChats` brings back Chats saved in linked Worktrees. None of that happens here: the saved state is answered as reconciled in memory. At start Node also loads every recent Project with a pending turn (`resumeRecentProjects`); this owner loads nothing until a `project:read`. A data dir Node served last already holds the results of those saves.
- **No events.** Nothing changes, so no `project:state` is published (Node publishes one on a scope's first `state:read` and on every change); only the wire's `daemon:stopping`. `version` is always 1 and `epoch` is a new random id per run; `eventSeq` stays 0.
- **Registry without writes.** Node's `project:known` scans `~/Developer` and `~/.milagre/worktrees` for coordination files while the registry isn't marked `scanned`, and drops entries whose folder went away through a write that checks every entry with Git. Here: no scan, no write; an entry whose folder (or Git directory) is gone is left out by a stat. Ordering compares `openedAt` by bytes (Node: `localeCompare`; the same for ISO timestamps). Saved paths outside the copy are left out of both lists.
- **Not served yet:** the Chats home (`project:read` of an existing one answers `NOT_SUPPORTED`), Links (`state:read`, `chat:messages`, `chat:message` of a `milagre-link:` scope answer `NOT_SUPPORTED`; the snapshot's `links` is empty), every write, send, provider, setting, account, Routine, phone, computer, `desktop:*` and `project:open`. `project:current` answers only on a connection that read a Project with options (the wire routes it to `project:snapshot`), as Node's does with a view.
- **Git discovery** is `milagre-registry`'s hardened `identify` (`/usr/bin/git`, no global config, a 3 s limit per command): it refuses repositories Node would open (symlinked or hard-linked metadata, config includes, `core.worktree`, more than 4,096 metadata entries, implicit bare repositories, Git directories outside the copy). Origins run `git remote get-url origin` in this process's environment as Node does; `originId`'s URL parsing is ported for the forms Git reports (equal to Node's on 25 forms) without IDNA or percent-encoding of hosts and paths.
- **Chats removed by reconcile:** `chat:messages` answers an empty page for a Chat whose Worktree went away, as Node's state does; `chat:message` still finds such a message in chats.db.
- **Arguments:** `--app-version` is required (Node defaults to its package version); D must exist (Node creates it); `--cwd` is accepted and unused (it only picks `project:current`'s launch Project); only `serve` exists (no `status`, `stop`, `request`, `bridge`). Stdin EOF stops it (Node ignores stdin). Authentication (Windows) isn't supported.
- **Stop order:** Project and repository locks, then the socket, then D's lock (Node releases its runtime's locks, then closes the socket). A failed stop keeps the owner up refusing commands, as Node's does; `daemon:stop` can be sent again.

## Checks

```sh
cd experiments/rust-profile-owner
cargo test                                   # needs Node 24 and the repo's npm ci; run with env -u ELECTRON_RUN_AS_NODE from a Milagre terminal
cargo clippy --all-targets -- -D warnings
cargo fmt --check
```

- **Unit (8):** argument parsing; isolation lookup refuses a data dir outside any copy, a copy around a registered Project and the account home's Milagre folders; reconcile (read fields, idempotence, a Chat made for a Worktree without one, no saved state); `originId` forms.
- **`tests/refusals.rs` (5), the binary without Node:** the socket path is the Rust client's own derivation (0600 socket, 0700 folder); `owner.json` is byte-for-byte `JSON.stringify(owner, null, 2)` with the keys in Node's order, 0700/0600; a second owner by path or by a symlinked alias is refused with the lock unchanged; stdin EOF releases lock and socket; a data dir outside a copy and the copy root are refused before any write; the installed profile and `~/.milagre` are refused with their lock untouched, and a chats home or Worktree root under `~/.milagre` too; a dead owner's lock is refused and left byte-identical; a regular file at the socket path is refused and left (and the lock released), a crashed owner's socket is replaced.
- **`tests/origin_node.rs` (1):** `originId` against Node's own module on 25 remote forms.
- **`tests/node_differential.rs` (1)** with `tests/node-differential.cjs`, everything in one new copy under the system temporary folder (HOME, data dir, chats home, Worktree root, Projects):
  1. Projects with saved Chats are written with Node's `saveProjectState`: `alpha` (plain folder: 3 Chats, one archived, a subagent transcript and a step detail in sidecars, Unicode) and `beta` (Git repository with an origin remote: 1 Chat). This repo's Node daemon (`cli.cjs serve --data-dir D --app-version 0.0.0-test --cwd / --chats-home … --worktree-root …`, `HOME` in the copy) registers them with `project:open`, hides `beta`, then a second run records 32 reads through `apps/daemon/src/client.cjs` (unopened-Project page, refusals before opening, `project:read` in every form for both, snapshots, `state:read`, pages with `turns`/`limit`/`before`, `chat:message` with a sidecar detail, `chat:runs`, unknown Projects, an unknown command, the snapshot whole and paged) and stops with `daemon:stop`.
  2. The Rust owner serves D; the same 32 reads through the same Node client equal Node's, key order included. Normalized: `epoch` and `version` of `project:read`/`project:snapshot`/`state:read` (each host numbers its states in its own random epoch) and the snapshot's `eventSeq` (events that host published). Its status is Node's shape with exactly the methods above. Node's `serve` on D fails meanwhile ("Milagre state is already owned").
  3. `InstalledOwner::adopt_profile(D)`, `known_projects`, then per Project `project(path).connect`, `load_view`, `runtime_snapshot` + `accept_snapshot`, a Chat page, `project_read`, `state_read`, `chat_runs`: all succeed, unchanged client.
  4. `daemon:stop`: exit 0, socket, D's lock, both Project locks and the repository lock gone; all 67 entries of the copy byte-identical to before the Rust run (content hash, mode, type).
  5. With Node serving D, the Rust owner refuses (D's lock) and leaves Node's socket; a Rust run stopped by stdin EOF leaves the copy byte-identical; Node then serves D again and answers the 32 reads as it did before the Rust runs.

These are reads of throwaway data on macOS (arm64), not evidence about live profiles, sends, events or performance.
