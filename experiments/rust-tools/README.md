# Native content MCP dispatcher

This isolated library runs the retained Design and Artifact tool definitions without Milagre's Node MCP server or Node SDK. It provides no listener or provider transport of its own and cannot open a live profile. The production host remains the sole live writer.

## API and owner contract

`ContentOwner::open(isolation, artifact_relative_path, kit_relative_path, project_for_chat, owner_active, runtime, raster)` opens the native `ArtifactStore` and `DesignKits` exactly once and returns `Arc<ContentOwner>`. `owner_active` verifies the authoritative content owner identity. `project_for_chat` must admit only real, opened Chats whose Projects the runtime owns, and return their canonical Project identity. The stores use these callbacks for their existing scope and write checks.

`owner.session(caller)` returns a lightweight `Dispatcher` over the same owner. `Caller` is an immutable owner-supplied Chat/Project identity, admitted Worktree roots, read/write permissions, separate HTML/Design/kit grants, Design-id scope, bundled skill directory and revocation callback. Its Project must match the authoritative resolver. No MCP argument replaces a grant. Every storage operation installs a scoped authorization lease on both stores, composing the base owner check with the current caller's revocation and Project-identity checks. All existing atomic-write checkpoints check that lease; Drop restores the base guard on success, failure or unwinding.

- `session.list()` returns implemented/granted schemas, descriptions and annotations.
- `session.call(name, arguments).await` returns MCP `{content, isError}`, including PNG blocks. `session.dispatch(frame).await` accepts one complete JSON-RPC frame and returns bytes or `None` for a valid notification. Both use `&self`, so independent sessions can share the owner.
- `owner.renderer(&scope, method, request)` implements the existing `artifact:list`, `artifact:get`, `artifact:asset`, `artifact:comments` and `artifact:apply` routes synchronously through those same stores. The owning runtime first mints `scope` with `owner.renderer_scope(chat, expected_project, guard)` after authenticating its renderer. This private capability is bound to that owner, Project, Chat and revocation guard; MCP Caller values and sessions cannot become renderer authority. They create no second writer.
- `owner.storage_fault()` reports latched unsafe-file, corruption, I/O and ownership failures. `owner.shutdown()` invalidates every retained session and drops both store handles under the lane before returning, even while session Arcs remain alive. It is idempotent; the runtime may then release its outer owner lock. Old sessions never attach to a replacement owner.

The full grant advertises 14 tools: `design_show`, `design_read`, `design_inspect`, `design_validate`, `design_apply`, `design_export`, `design_list`, `design_kit_read`, `design_kit_save`, `artifact_show`, `artifact_read`, `artifact_list`, `artifact_comments`, `artifact_resolve_comment`. `design_delete` remains excluded because the content store has not implemented it. Browser, voice, publishing and unrelated tools are absent.

One mutex serializes admission, reads, optimistic revisions and writes across Chats and both callers. PNG rendering starts only after the commit releases this lane. Another Chat or the renderer can read/edit while the first caller awaits its image; that image always uses the saved snapshot from its own revision. All calls recheck their grants before returning content. If revoked during PNG feedback, the caller receives an error with no saved content or image, while the committed version stays saved. Cancellation also leaves an already committed revision intact; adapters must not replay it. Shutdown closes storage immediately after the current synchronous operation; an in-flight PNG helper remains bounded by its existing timeout and cannot return content to a closed owner.

Synchronous store operations, admission and authority callbacks run behind `catch_unwind`. A panic permanently faults and deactivates the owner; no later operation resumes its potentially inconsistent state. Public errors use a static message without the panic payload. Mutex poison is recovered only to report the fault and perform cleanup. `shutdown` handles poisoned lane, fault and wake locks, takes both stores out of the lane and drops them before returning, even when old session handles remain. It does not assume a panicking write rolled back, and it never retries it. Three regression tests cover an operation panicking after a commit, authority callback panics, each poisoned lock, refused later calls, idempotent shutdown and reopening the released stores in a fresh owner. Rust panic-abort builds and process aborts cannot be caught by this mechanism.

The convenience `Dispatcher::open` remains for single-Chat fixtures. Runtime code must use the shared `ContentOwner`, not open it alongside another ArtifactStore on the same directory. Session futures are `Send`; the synchronous schema/layout/storage phase should run on the owner's dedicated worker rather than block a shared async I/O executor. This crate provides storage serialization, not provider-run scheduling.

## Async execution and cancellation

`call` and `dispatch` move parsing, filesystem callbacks, native layout, storage, feedback and serialization onto blocking workers. The owner accepts at most 16 concurrent calls/frames across every session, including queued operations and pending PNG feedback. Excess requests are explicitly refused before acceptance. One standard mutex remains the sole storage lane; no Tokio lock is held across synchronous storage. RPC execution does not nest blocking workers, including with a single-worker Tokio pool. Public synchronous APIs (`open`, session admission, `list`, renderer routes and `shutdown`) must be invoked by the runtime owner worker, not an async executor thread.

Adapters that need cancellation evidence use `session.start_call(name, args)` and retain `accepted.receipt()` before awaiting `accepted.wait()`. A receipt contains only phase, mutation outcome and a cancellation flag, no request/reply content. Dropping/cancelling queued work records `CancelledBeforeStart` and skips its handler. Once inside the storage lane, cancellation lets that single operation finish; it cannot unlock the stores or start a replacement writer. The receipt records `Committed` as soon as a mutating handler succeeds, before PNG feedback. Errors after a mutation handler starts conservatively record `Uncertain`, even if a particular error probably rolled back. Validation/authorization failures and reads record `NotAttempted`. Retained receipts have no owner-global history or unbounded accumulation.

A cancelled waiter must never trigger automatic replay. Read the receipt and authoritative saved state before deciding on a fresh operation. `call` is the compatibility wrapper and `dispatch` preserves JSON-RPC result shapes; dropping either has the same queued-versus-started boundary, but a transport that loses its reply must conservatively treat a write as uncertain. No new daemon endpoint is introduced. Blocking workers finish accepted writes even after the awaiting future disappears; owner shutdown still invalidates grants and waits for the current storage operation before releasing its lock. PNG feedback remains bounded by the helper and retains its accepted-call slot until it finishes.

Tests use a single-thread executor with a staged write deliberately blocked by a guard: timers still run, cancellation during storage commits exactly one revision, 15 queued cancellations write nothing, and a seventeenth call is refused across Chats. Other tests cover receipt outcomes, a single blocking-worker RPC runtime, and committed receipt visibility while PNG is pending. Normal successful tool results still match the actual Node fixture.

## Existing behavior preserved

`src/contract.json` is generated from actual `artifactToolDefinitions`, `htmlArtifactToolDefinitions`, `designKitToolDefinitions` and the local Designs group's `design_list`. Descriptions replace only the installation-dependent bundled-skill directory. The advertised schemas remain exactly Node's JSON Schema; a separate generated parsing snapshot records Zod's strict/strip/passthrough behavior. The Rust interpreter rejects unsupported schema keywords, enforces strict top-level arguments, handles record keys, discriminated alternatives, integer bounds and installed Zod's Unicode code-point string limits. Unknown fields in open layer inputs still reach the stricter native Design engine, as in production.

Show/apply commit fresh native HTML before computing feedback. Feedback preserves summary JSON on the first line, warning limits, intent-specific guidance, font/glyph limitations, remote-image notes and PNG blocks. A failed or unavailable preview adds the existing warning and does not undo an already saved version. Inspection includes bounds, crop, diagnostics and preview limitations. JSON/SVG exports, validation, pinned kits, tab selection and comments use the native store, with the existing version/conflict rules. PNG compression bytes may differ; decoded pixels match the Node WASM renderer in tests.

The helper binary is `milagre-design-raster`, built from the content-store helper entry point. Pass a trusted absolute executable path in one shared `RasterRenderer`; never accept a helper path from a tool argument. A `None` renderer deliberately exercises production's saved-version/failed-preview behavior, with an explicit unavailable-helper message. Packaging the helper and connecting tool images to the provider remain integration work.

Scoped Designs filter discovery, saved ids and comments. This implementation also checks `from.id` when copying a variant; current Node checks only the target id, so Rust deliberately prevents copying an out-of-scope source. Worktree roots must resolve to directories inside the Isolation. Their canonical location is rechecked with the caller's guard, so replacing a root with an outside symlink stops later requests. This is not protection from arbitrary external filesystem changes between individual syscalls.

## Protocol and limits

The dispatcher implements `initialize`, `ping`, `tools/list` and `tools/call`, with production protocol versions `2025-03-26` and `2025-06-18` and serverInfo `{name:"milagre",version:"1"}`. Unsupported requested versions negotiate to `2025-06-18`. Unknown tools return the existing tool-error content; unknown methods return `-32601`. No resources or prompt capability is advertised.

Frames are limited to 1 MiB, except Design show/apply at 6,000,000 + 64 KiB. Replies are capped at 32 MiB. Input parsing retains lone UTF-16 surrogates through the existing `jsjson` representation. Nested schema interpretation stops at depth 80; JSON parsing has its existing recursion limit. Calls share the ContentOwner storage lane; the native raster helper separately bounds its queue and process lifetime.

There is no HTTP, stdio, bearer-token, grant registry or Claude/Codex transport adapter. Thus malformed frames produce ordinary JSON-RPC parse/invalid-request errors instead of the Node HTTP server's empty 400 response; oversize requests produce `-32000` without an HTTP status. The future transport must enforce authentication, framing, connection revision, HTTP headers or provider-specific routing before calling this library. It must not replay a call after cancellation: a write may already have committed before PNG feedback finishes.

## Independent host role guard

`owner.session(caller)` preserves ordinary grants. `owner.session_with_policy(caller, policy::PolicyOptions)` admits an immutable `HostRole` and optional manifest subset. The native handler registry classifies each implemented operation's effect; admission checks generated Node annotations against that registry. `owner.host_session(caller, options, registrations)` assembles that same capability with other implemented owner handlers. A `RegisteredTool` owns its schema, `ToolEffect` and callback privately. Registration refuses native-name shadowing, duplicate names, misannotated effects and use of `WakeResponse` for anything other than `chat_respond`. No registrations are read from transport input. Registration is trusted runtime code and must use the actual handler's schema and effect. An owner-supplied manifest can only narrow registered/granted tools and must match each effect exactly. Unknown names, duplicate names, unsupported handlers and relabeled writes fail admission. The resulting private manifest drives both `tools/list` annotations and `session.provider_manifest()`; adapters must use that snapshot rather than independently assembling tool metadata. Changing the returned snapshot cannot mutate the session. `session.endpoint(names)` narrows routing for a transport or registry while retaining the same policy, budget, wake and immutable caller; narrowing cannot widen later. `host_manifest()` reports the entire admitted host manifest, while `provider_manifest()` and `list()` report that endpoint's subset. Content and external handler calls reserve slots from the same atomic counter. Register all supported handlers once, then derive endpoints from that capability rather than creating an independent policy per registry.

Every direct `call` and JSON-RPC `tools/call` enforces that manifest before argument validation or execution, even when no provider adapter is involved. Provider `Full`, `readOnlyHint`, permission metadata and caller write permission cannot override the role. Role and wake scope have no mutation API. `AnalysisAdvisor` exposes only the nine read operations. `Babysit` and `ExecutionAdvisor` are unsupported and fail before a session is created.

`owner.issue_wake(&caller, requests)` creates an opaque `WakeLease` bound to this owner, caller Chat/Project and the immutable request pairs. `PolicyOptions::escalation(lease, on_sealed)` constructs its role; hand-editing the role ID or pairs fails admission. The stop callback must be nonblocking. Ordinary native sessions still expose only reads under escalation because this crate has no production `chat_respond` handler. A trusted owner may register an implemented `WakeResponse` handler; escalation admits it only for the exact wake pairs, while Analysis refuses it. The handler must validate the decision and payload beyond those pairs before committing. Unsupported responses remain unavailable rather than stubbed. Explicitly requesting any unsupported or write capability for a constrained session fails admission instead of silently replacing it with Ordinary.

Escalation atomically reserves one slot for every attempted host tool call, including unavailable tools, bad arguments and repeated JSON-RPC ids. Exactly six calls can reach execution. Attempts seven and eight return Node's reply-now message; the ninth seals the budget and invokes the owner's stop callback exactly once. The counter saturates at nine, and a callback panic cannot unwind the dispatcher or reopen the budget. `session.budget_status()` reports attempts and sealed state. A sealed callback must reliably signal the provider turn; the host itself starts no provider and cannot confirm that the provider stopped.

A wake lease can be admitted only once, including after its endpoint is dropped. `lease.release()` invalidates all derived endpoints and the authorization checkpoints of an in-flight operation; a released lease can never be admitted again. Owner-issued IDs use checked monotonically increasing sequences, and the opaque lease also binds its owner identity. Foreign leases and forged role strings fail admission. There is no retained wake-name set, lifetime admission cap or tombstone accumulation. A caller retains only the leases and endpoints it needs; the runtime releases a lease when the wake ends or startup fails. A fresh owner-generated lease is a new wake, never a reset of an existing capability.

External callbacks run outside the content storage lane, on separate named threads with eight owner-wide execution permits. An actor can service a renderer operation before replying to the callback without a lock cycle. Each call has a ten-second deadline; trusted registration can shorten it with `with_timeout`. Cancellation/deadline returns an explicit error and marks an already-started write uncertain, with no replay. `HostContext::assert_active()` checks the deadline, cancellation, per-call close, wake, caller and owner; handlers must invoke it at every commit checkpoint. It is checked before and after the callback too. Rust cannot safely kill an arbitrary synchronous callback: one that ignores cancellation keeps its execution permit until it exits, so repeated timeouts cannot spawn unlimited workers. Native content calls retain their separate writer and can proceed while these callbacks wait.

Registration validates a strict supported JSON-schema subset rather than silently skipping unsupported assertions. Root and nested objects must name their properties and forbid extras; required fields, types, enums, arrays and numeric/string/item bounds are enforced on the unchanged arguments before callback invocation. Unsupported schema assertions fail registration. `WakeResponse` requires string Chat and request fields; the exact wake pair is checked again after validation without consuming a second budget slot. Handlers still enforce semantic constraints the schema cannot express, including authoritative ownership and whether the requested decision is currently valid. Callbacks remain private to the guarded dispatcher. No production Chat or Worktree service is added by this registration API.

The external boundary tests cover a handler whose actor reply is sent only after a renderer call, eight blocked handlers retaining capacity after cancellation/timeouts, rejection of a ninth without starting it, native reads during those waits, failed late commit checks and strict payload/unsupported-schema refusal. Timeout receipts remain conservative even when a specific fixture proves it wrote nothing.

Thirteen host-policy tests cover the native manifest and previous role restrictions, a whole-host manifest narrowed across two endpoints, parallel calls across content and external chat fixtures sharing exactly six successes, a single stop after two grace denials, endpoint crossing, wrong wake pairs, invalid response payloads, Full/read-only metadata bypass attempts, unlisted and misannotated handlers, callback panic and release during an in-flight handler. They also exercise 1,024 sequential wakes, retained/reused/foreign lease refusal and forged role association. The runtime-generated fixture still compares twelve calls with the real Node `EscalationTurn` budget and stop behavior. Provider-native tool events retain their separate full-turn guard; these tests verify the independent host boundary, not constrained provider startup.

## Verification and gaps

```sh
cargo test --manifest-path experiments/rust-tools/Cargo.toml
cargo clippy --manifest-path experiments/rust-tools/Cargo.toml --all-targets -- -D warnings
node_modules/.bin/oxlint experiments/rust-tools/fixtures/*.cjs
```

Thirty-four tests currently pass. The conformance fixture executes 63 calls through Node's actual command dispatcher and actual content/kit stores in a temporary Isolation. It compares tool success/error shapes, text lines, parsed JSON values and decoded PNG pixels, including create/edit/variant/inspect/export/validate, kit conflicts, HTML tabs, comment resolution, field errors and supplementary Unicode. One comment snapshot is seeded from Node's real `addComments` output to represent a user-authored comment. Generated schemas, descriptions, annotations and source hashes are checked against current Node every run. No network server, provider turn or production data is involved.

Boundary tests cover protocol negotiation, notifications, unknown tools/methods, malformed and oversized frames, UTF-16 request ids, unsupported-tool discovery, read-only grants, allowed/forbidden Design ids and comments, cross-Chat argument rejection, variant-source containment, grant revocation, swapped Worktree roots, corrupt-storage latching and `Send` compatibility for an owner actor.

Shared-owner tests add two concurrent Chats, concurrent renderer/MCP expected-version conflicts, shared Project kits, cross-Project/Chat/grant denial, independent revocation, owner-identity loss, reads during pending PNG, revocation during PNG without undoing a commit, shutdown with retained sessions and reopening the released stores. Separate mid-commit tests revoke a grant after Design HTML staging and before a kit rename: the staged write rolls back, the original version stays readable, and another grant can still write. This verifies both scoped guards are restored rather than leaking the revoked grant into the shared owner. Caller lease and admitted-root I/O errors during staging refuse that caller without faulting the shared storage owner. Owner identity and storage failures still fault the owner. Renderer tests reject wrong owner, Project, Chat and revoked capabilities, including a retained capability after reopen.

Remaining limits: the 63-call fixture is not exhaustive; native Design-engine structural error wording can still differ from Zod's complete diagnostic envelope (the content-store README documents this). HTTP and SDK-adapter interoperability, provider-run scheduling, desktop/mobile events and installed WebKit behavior are not verified by these tests. No user-facing service is advertised as migrated because this library passes.
