# Persistent synthetic authority checkpoint

`persistent::PersistentAuthority` consumes a WriterLease from a freshly created SyntheticProfile. It reuses the existing policy/admission/crypto implementation and privately owns its bound Registry. The old TemporaryAuthority and Supervisor constructors retain their disposable behavior. There is no existing-profile/path/FD/key importer, public subprocess launcher or persistent supervisor.

## API and ownership

`resume(writer, PersistentLimits { policy, registry }, rng)` returns `OpenedAuthority::Ready`, `Quarantined` or `Retired`. Every outcome owns the moved lease. Ready exposes owner operations for pairing, desktop enable/approval, removal, and synchronous in-memory carrier/request dispatch. Its registry, Session, storage and writer cannot be extracted. Desktop access and pairing windows start closed on every run; a trusted owner explicitly calls `enable_desktop` and `open_pairing`. `with_pairing_invitation` borrows the generated synthetic token only within an open window. This is a trusted owner API, not an authenticated remote endpoint or authority inferred from a carrier message.

`close_for_restart(self)` revokes all issued access and clears tickets, closes carriers and cancels queued/inflight requests before terminal IO. It commits Clean, syncs, releases both writer locks and restores the matching retained-broker acknowledgment. Success returns CleanStop. `retire_identity(self)` performs the separate terminal Retired transition and returns RetiredStop. A retired snapshot cannot become Ready again.

Either consuming close can return CloseFailure. `into_parts()` yields `(StoreFault, StoppedAuthority)` with the already stopped writer still owning both locks. This guard, Quarantine and RetiredProfile expose only redacted diagnostics/release. There is no retry-Clean, replay, reset or unquarantine operation. Drop revokes runtime access and releases ownership without writing any snapshot or acknowledging Clean. IO ambiguity, exhausted persistent generations and prior fatal policy revocation prevent clean close.

The synchronous layer starts no task or thread. Test brokers join their own children. Supervisor integration must separately retain and join worker ownership before reporting a successful close. Wrong-PID entry refuses before inherited runtime locks. Wrong-PID teardown closes only child writer aliases and deliberately abandons inherited runtime allocations until child exit, avoiding inherited mutexes. Continuing a multithreaded authority after fork is unsupported; the supported private test bootstrap execs a fresh worker with an unlocked root descriptor.

## Persisted authorization and format

The authority durably increments boot generation and writes Running before returning Ready. Pairing-window and removal changes advance durable policy generation. A removal first revokes the device epoch and registry work, then commits its tombstone. An ambiguous mutation retires all runtime access and makes the next run quarantine, even if the previous active record remains on disk. Enrollment commits before Accepted can release a channel; consuming completion also checks that the target carrier is still pending before attempting persistence.

Device epochs and the last removal generation survive re-pairing. Runtime removal timestamps are never compared across boots. A loaded tombstone requires a later explicitly opened durable window. Within one run, removal and reopen in the same millisecond remain refused, matching the existing Node predicate. The active-device limit is separate from lifetime history: default 64 active, up to 4,096 distinct historical keys. Full history refuses unseen enrollment while allowing known reconnects, removal and re-pair. Tombstones are not evicted and 64 removals do not retire the authority.

The final v1 disk schema follows the agreed status names: `identity_status` is `current` or `retired`; `run_state` is `clean` or `running`. Each device has `key`, `kind`, `epoch`, `state` (`active`/`removed`) and required nullable `removal_generation`. Active re-paired entries retain that last removal generation. This replaces the descriptor-only checkpoint's preliminary boolean/nullable-state spelling; there is no importer for that preliminary format. All tests create fresh synthetic stores. Unknown/missing/duplicate fields, inconsistent generations, noncanonical encodings and over-bound allocations are refused.

Tickets, Sessions, carrier handles and work cursors carry the opaque profile/identity/boot/runtime binding. WorkTokens inherit the handle binding. Repeated synthetic random nonces cannot make a successor accept an old ticket or callback. A bound registry also rejects an otherwise live Session from another profile. No crypto counters, channels, pending grants, output buffers or requests resume across a close.

The store's 12 MiB working reservation now shares the authority's 256 MiB global pool with every device/connection lease. It covers bounded snapshot input/output, typed state, maps and candidates; it remains charged while the profile capability lives. The allocation test observes actual codec plus policy-hydration map allocations for 4,096 records, and candidate clones, against the two 3 MiB parsed-state allowances. Container counts are bounded before insertion; standard Rust BTree allocation retains Rust's process-level OOM behavior. No secret-zeroization or encrypted-at-rest claim is made.

## Evidence

1. Same-process clean replacement preserves synthetic box identity, token, kinds and epochs. Windows/desktop approval close; retained Session access, tickets, handles, cursors and callbacks cannot revive. Queued/inflight requests cancel and owned connection leases release. Tests force repeated RNG output to exercise generation binding independently of random uniqueness.
2. A fixed private subprocess worker enrolls once, closes cleanly, and reconnects as known in a fresh process. The broker accepts only its own joined worker's exact attempt/revision/boot receipt. Drop, lost acknowledgment, failed final directory sync, and abrupt process exit after removal revocation but before tombstone write all quarantine the next run. The latter verifies cancellation before exit. Public process supervision remains absent.
3. Running, window, enrollment, removal, Clean and retirement failures are injected at write/file-sync/rename/directory-sync boundaries. Consuming failure retains Busy writer ownership until explicit guard release; failed writes never replay implicitly. Counter exhaustion, full configured history, 70 removals, strict-time re-pairing, closed-carrier completion and invalid configuration are covered. macOS disk/subprocess unit scenarios are serialized because fork briefly inherits unrelated CLOEXEC descriptors before exec; production nonblocking Busy behavior is unchanged.
4. Six existing Node transport/service checks remain unchanged. `tests/restart-node.mjs` adds an inventory fixture by executing the actual devices.cjs source with a closed in-memory dependency set. It covers phone/computer kinds, metadata/notice fields, reload, removal/re-pair and Node's malformed-file empty fallback. It reads source only, never the daemon startup graph or a profile. The existing policy-node fixture still verifies actual Node pairing-window predicates.

Validation: 159 tests and seven doctests pass, along with strict all-target Clippy and all seven Node checks (six existing transport/service checks plus the new persistence inventory).

## Remaining gates

This synchronous API does not extend pending carrier deadlines while desktop approval waits; that bounded wait/lifecycle wiring remains a supervisor responsibility. Admission lockout diagnostics are exposed through `admission_status`; relay sources still have no invented per-phone IP identity.

Persistent supervisor integration, public broker transport, broker-loss/reboot recovery, real HTTP Claim/cancellation, network carriers/listeners, relay/host lifecycle, live pairing and actual phone interoperability remain unimplemented. Owner queue reservation versus duplicate DrainWork, Disconnect saturation and fairness remain separate P3 gates. No existing keys/profile/data, mobile code/native fingerprint, production host, daemon writer or push is involved.
