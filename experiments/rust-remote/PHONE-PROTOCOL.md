# Phone assembly and dispatch checkpoint

This checkpoint adds `phone::{request_parts,response_parts,RequestAssembler,Dispatcher,JsText}` and `Channel::open_encoded`. It runs only in memory, including the encrypted fake-carrier test. There is no HTTP server, WebSocket connection, forwarding fetch, production profile, pairing approval, service ownership or mobile change.

## API and boundary

`request_parts(&Request)` emits UTF-8 JSON byte vectors with the mobile transport's `{t:"req",id,method,path,headers,chunk,more}` fields in order. `response_parts(&Response)` emits `{t:"res",id,status,headers,chunk,more}`. Chunks contain canonical padded base64 of at most 256 KiB; empty bodies emit one final part with `chunk:""`. Headers preserve insertion order through `IndexMap`. HTTP metadata has typed scalar strings; bodies remain opaque bytes. Request methods are GET and POST. Paths must start with `/` and not `//`, matching Node's `routeOk`; this is not URL confinement or authorization.

`RequestAssembler::receive(bytes, now_ms)` collects interleaved uploads by safe-integer ID, retaining the first part's metadata and returning a complete `Request` only on its final part. Current mobile repeats all metadata in every part; later metadata is parsed but ignored as Node does. It has no active-fetch queue: a caller must enforce the existing 16-active/64-queued scheduler, 20-second queued-request deadline, header filtering, bridge-origin confinement and method allow-list before forwarding. Authentication and pairing approval must already have completed. A completed request is data, not permission to execute it.

`Dispatcher::begin(deadline_ms)` reserves a unique increasing request ID. `subscribe()` reserves a live ID from the same sequence. Call `receive(plaintext, now_ms)` for authenticated host JSON. It returns `(Vec<Event>, Result<()>)`; always consume events even on an error, because they include disconnect teardown. Events include complete responses, request failures, live data/close and `SendPong`. Responses for unknown or cancelled IDs are ignored. First response status/headers win across chunks. A malformed response for a known ID fails that request and releases its assembly without preventing later valid batch items from dispatching. Live-close removes that subscription; late data for it is ignored. Unknown tags are ignored, as mobile does.

Batch items are flattened depth-first in their original order. All batch structure is checked before any item is dispatched. Then response/live/ping effects are produced in order, matching the extracted production mobile dispatch trace. This does not implement the host's outgoing 50 ms / 512 KiB batching scheduler or the caller's callback/reentrancy behavior. The caller must act on the returned events, including sending pong and scheduling live reconnection.

## Bounds, timeouts and cancellation

| State                  | Limit / behavior                                                                                                                                                                                                          |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Incoming JSON          | Existing relay payload limit minus 25 bytes of channel overhead.                                                                                                                                                          |
| Body chunks            | At most 256 KiB decoded; canonical padded base64 only.                                                                                                                                                                    |
| Host upload            | Default 8 MiB **estimated** body size. Node adds `floor(chunk.length * 3 / 4)`, including padding overhead; Rust preserves that quirk. An exactly 8 MiB body split at the standard boundary is rejected by this estimate. |
| Host retained state    | At most 80 incomplete uploads; default 16 MiB aggregate decoded body plus retained path/header string bytes. Configurable within fixed ceilings. No active/queued HTTP work is counted because none is started.           |
| Client retained state  | At most 80 pending requests and 8 live subscriptions; configurable aggregate retained response bytes/headers up to 64 MiB. Each response body is capped at 64 MiB.                                                        |
| Cancelled upload tails | At most 64 abandoned IDs, released on their final part or disconnect. Exceeding this bound closes the assembler.                                                                                                          |
| Batch                  | At most 4096 total nodes including batch containers, depth at most 16. Checked before producing message effects.                                                                                                          |

`now_ms` and deadlines are caller-supplied monotonic milliseconds. There are no internal clocks, sleeping tasks or timers. The caller must schedule `expire(now_ms)` even while no bytes arrive. Request assembly defaults to a 20-second **local upload lifetime**, fixed at the first chunk; receive also checks the deadline for the incoming ID. This is added admission hardening: Node's partial upload has no equivalent deadline, and its 20-second timeout applies to completed queued work. Expire other IDs before admission to free their slots. Time arithmetic is checked. Defaults are not negotiated on the wire.

Client deadlines are passed explicitly to `begin` so slow methods can retain their longer existing deadlines. `receive` expires requests before dispatching its frame; at the exact deadline timeout wins. `cancel(id)` removes local pending response state. Neither timeout nor cancellation emits a nonexistent wire cancel command. Node `client.ts::overRelay` likewise only stops waiting; host execution may still finish. Cancellation of an HTTP fetch, queued execution, mutation or live subscription must be handled by its owning service.

Host `cancel(id)` releases an incomplete upload and ignores its remaining chunks through the final part. Host schema/size/admission failures close and release the whole assembler; production Node often emits 400/413/429 instead. Mapping refusals to responses and managing its rejected-ID lifecycle without dropping healthy requests is future service work. Dispatcher protocol errors return disconnect events and clear all state. Individual bad response bodies fail only their pending request.

`disconnect()` releases maps and buffers, returns affected request/live IDs as appropriate, and permanently closes that instance. Reconnection uses a new channel and dispatcher generation; never route old socket callbacks into it. No request ID is reused within one dispatcher. Multipart bodies have no part index or checksum: order/replay protection belongs to the encrypted channel. The assembler cannot detect an application duplicating a chunk under a new valid counter.

Limits account for retained payload/metadata string lengths, not allocator capacities, JSON parser overhead, event vectors handed to the caller or total RSS. The caller must also bound concurrent sessions, outgoing encoded vectors, queued HTTP work and socket buffers. Writers currently materialize all parts.

## JavaScript strings and owner `jsjson`

Incoming lone surrogates must not pass through `serde_json::Value` before the owner's lossless parser. `Channel::open_encoded` authenticates bytes and advances the receive counter without parsing JSON. Feed its output directly to `rust-owner::jsjson::parse_bytes` at the integration boundary. That parser is owned by the parent crate; this checkpoint adds no dependency on, copy of, or changes to its implementation. Raw output can be invalid JSON; the caller must reject it and close the connection. `Channel::open` remains the convenience scalar-Unicode decoder and still rejects lone surrogates.

For `live.data`, `JsText` holds the original JSON string token through `serde_json::RawValue`. `as_json()` preserves `"\ud800"`, real U+F0000, real U+10FFFE and combinations distinctly. Parse that token once with owner `jsjson::parse` before using its UTF-16 helpers. To send an owner value back, use **owner `jsjson::to_string`**, then `seal_encoded`. Never serialize an owner-encoded `Value` or string with ordinary serde: its internal escape/PUA representation would leak onto the wire or collide with real text. `JsText::to_unicode` explicitly fails on lone surrogates; it is not the lossless owner adapter.

HTTP request/response bodies are bytes, so embedded JSON and its escaped surrogate data are preserved without interpretation. Header names/values and request paths still use ordinary Rust strings and reject unpaired surrogate escapes. Hello metadata parsing remains a scalar-Unicode path. The subsequent safety checkpoint changed desktop `FrameReader` to leased raw JSON, including lone surrogate escapes and PUA; see SAFETY.md. Batch tags and IDs have typed parsing. Invalid UTF-8, certain duplicate fields, noncanonical base64, unsupported/deep structures and out-of-range numbers remain stricter than Node. Generic numeric header keys may have different serialization order from JavaScript integer-property ordering when callers build an `IndexMap` directly. **This checkpoint does not claim compatibility with all valid Node JSON payloads.** Routing all remaining owner-facing JSON through a shared lossless boundary remains an integration gate.

Tests preserve exact authenticated raw bytes and compare actual mobile dispatch output containing both unpaired surrogate escapes and literal PUA/noncharacter text. The encrypted in-memory carrier passes these bytes through host sealing, client opening and batch dispatch with replay rejection. The owner parser itself is not linked or exercised by these tests.

Future host proof must use a maintained Ed25519 implementation verified against synthetic Node signatures. This checkpoint introduces no signing primitive or crypto design. Webhook claim/delivery persistence, shared relay backpressure, HTTP authorization/header filtering, response error mapping, device store/approval integration and owner RPC dispatch remain missing. Temporary synthetic authorization records now exist separately in HOST-POLICY.md; production stores and services remain absent. ## Reproduce

```sh
cargo test --manifest-path experiments/rust-remote/Cargo.toml --locked
cargo clippy --manifest-path experiments/rust-remote/Cargo.toml --all-targets --locked -- -D warnings
cargo fmt --manifest-path experiments/rust-remote/Cargo.toml --check
cargo build --manifest-path experiments/rust-remote/Cargo.toml --examples --locked
node experiments/rust-remote/tests/phone-node.mjs experiments/rust-remote/target/debug/examples/phone_conformance
```

Also run the original `tests/node-fixtures.mjs` reciprocal crypto check as described in README. `phone-node.mjs --record` explicitly regenerates the committed synthetic fixtures. Normal verification checks source hashes and recomputes expected results first. It imports the actual `relay-rpc.mjs`, extracts unchanged `requestPart` and mobile `dispatch` function bodies, removes TypeScript annotations using Node's `stripTypeScriptTypes`, and supplies in-memory forwarding/callback stubs. It tests the assembly/dispatch branches, not the surrounding services. No daemon or provider fake is started. Node currently prints its experimental stripTypeScriptTypes warning.

The added 13 Rust tests cover seven body sizes around the 256 KiB boundary, interleaved uploads, first-metadata behavior, ordered nested batch dispatch, ignored late IDs/live data, authenticated surrogate/PUA preservation, cancel/timeout/disconnect, metadata and aggregate limits, count/depth floods, strict schemas, actual 8 MiB upload rejection and a complete 64 MiB response. Reciprocal Node checks consume seven Rust requests and seven Rust responses and compare the mobile event trace. This checkpoint had 31 Rust tests; the subsequent safety checkpoint raises the total to 42 tests plus three compile-fail doctests. This is library conformance, not native phone, LAN, relay or end-to-end owner interoperability.
