# HTTP Claim and cancellation proposal

Status: proposed contract for review, not an implemented API or production authorization. This checkpoint changes no dispatcher, network dependency, listener, endpoint, profile format, phone codec or mobile file. First implementation would be an in-memory adapter/state-machine fixture. A subsequent, separately approved loopback fixture would exercise a real HTTP library against a server created and owned by that fixture. Production integration remains gated.

## Proposed owner API and atomic admission

New types below are illustrative and require agreement before implementation. They belong to a separate fixture-enabled adapter mode; ordinary MemoryHttp dispatch keeps its present behavior. The carrier client gains no owner commands, request-body export or HTTP capability.

1. `owner.prepare_claim(work) -> Result<ClaimAttempt, ClaimRefusal>` allocates an opaque, service-scoped, non-Clone attempt with a checked monotonic id and a prepaid status slot. It binds the complete work identity: broker/profile identity, boot instance, carrier generation, device removal epoch and work serial. Proposed status limits are 512 per service and 32 per device, including submitted, active and unacknowledged terminal attempts. Exhaustion refuses admission without eviction or counter wrap.
2. `owner.submit_claim(attempt) -> Result<ClaimReceipt, ClaimSubmitRejection>` consumes the attempt only on successful enqueue. Full before enqueue returns its exact attempt for retry. Stopped, stale or expired rejects it terminally. The attempt's observation id is available before submission. A lost successful receipt permits only `observe_claim(id)` or cancellation, never reconstruction or resubmission. Duplicate ids cannot create operations.
3. The worker serializes claim with removal, replacement, expiry and shutdown. It checks the current authorization and scheduling deadline, reserves all adapter/executor, cancellation, completion, response and error resources, and prepares/validates the request before changing Ready to Claimed. Only one attempt can win for a work serial. Failure returns a recorded `NotClaimed` with zero adapter invocations and leaves eligible work Ready. A fresh attempt is permitted only after that definite refusal and within its original scheduling deadline.
4. Successful claim moves a non-Clone internal `DispatchPermit` and request lease into service-owned execution. Neither the permit nor a callback escapes to arbitrary caller code. A short Begin barrier serializes with revocation and records Dispatching/MayHaveStarted before permitting the first external action. No network wait holds the session revocation lock.
5. `observe_claim(id)` returns bounded execution/delivery state. `cancel_claim(id)` sets a prepaid out-of-band cancellation flag; it does not need ordinary command/event queue capacity. `ack_terminal(id)` releases the retained status slot. Missing, acknowledged or previous-boot ids mean Forgotten/Unknown, never proof of no execution. Observation cannot start or replay work.

DrainWork remains read-only and repeatable. In adapter mode, its eligible state is called Ready rather than implying an active fetch. Existing queued requests count toward scheduling limits; claimed requests retain their slot until terminal cleanup. Only accepted claims own executor slots. Idle clients or lost receipts cannot leave unbounded tasks/status records: limits refuse more work, deadlines cancel operations, and service disposal drains everything. An owner that never acknowledges terminal records can exhaust its own claim admission but cannot evict evidence and cause a retry.

## State, deadlines and outcomes

| State                      | Transition rule                                                                                                                           | Side effect permission                             |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| Queued / Ready             | A fully assembled request has one scheduling expiry, assembly time plus 20,000 ms. Promotion/Drain does not extend it.                    | None.                                              |
| Claimed                    | Atomic resource-complete claim records `claimed_at`; checked additions set HTTP deadline +340,000 ms and completion deadline +345,000 ms. | Only internal Begin may advance.                   |
| Dispatching                | Begin checks current generation, cancellation and deadlines, then marks MayHaveStarted.                                                   | One adapter invocation.                            |
| ResponseReady / Delivering | Full response accepted or prepaid 502/504 constructed. Output pump rechecks generation/deadline and emits ordered encrypted parts.        | No second HTTP invocation.                         |
| Terminal                   | Completed, NotClaimed, Cancelled, TimedOut, DeliveryUnknown or Failed, with separate execution/delivery evidence.                         | None; never transitions back to Ready after claim. |

Equality expires. Claim scheduling delay consumes the HTTP deadline; Begin at or after it is refused. Incoming chunks, output progress and repeated observations do not renew deadlines. Carrier idle expiry (normally 45,000 ms), removal, replacement and stop may cancel earlier. A manual-clock test must keep a healthy connection alive with ordinary traffic when testing a 340-second timeout. The five-second completion margin allows 504 encoding/delivery, not another fetch. A congested carrier may still expire before delivery, with no replay.

Applying 20 seconds to Ready as well as Node's waiting queue is an explicit additional scheduling bound. The adapter mode must prepay a small per-request error path on request admission so unclaimed scheduling expiry can produce Node's 429 without invoking HTTP. Invalid/oversized upload 400/413 and other existing close-versus-response differences remain separate codec/service work; this proposal does not claim they are already solved.

Execution evidence and delivery evidence are independent. Cancellation before Begin proves NotStarted. Cancellation after Begin is MayHaveRun, even when the adapter has not confirmed any transmitted bytes. A timeout, 502/504, lost command receipt, failed socket write or lost phone acknowledgment cannot prove a POST had no effect. Failed/unknown claims are never retried automatically, within the process or after restart. A new phone request id is not durable application-level deduplication. The protocol cannot promise exactly-once remote effects.

## Complete reservation and bounded streaming

The first fixture proposal uses bounded in-memory staging, with no new disk spool or store capability. The entire 64 MiB response allowance is reserved and fallibly allocated before Begin, plus bounded headers, read buffers, encoding scratch and an output window. This is conservative but avoids starting a POST whose maximum accepted response cannot be retained. Declared Content-Length never substitutes for reservation or actual byte counting.

Current 64 MiB connection and 32 MiB output defaults cannot retain a 64 MiB body plus framing overhead. They remain unchanged for existing services. The proposed explicit fixture limits are 128 MiB per connection/device, the existing shared 256 MiB global pool, two adapter executions globally and one per device. These are fixture resource choices, not Node's 16-fetch concurrency or a production tuning decision. Dynamic shortages still refuse before Begin. Parent agreement is required for this fixture configuration; accepting a smaller response cap silently is not an alternative.

Preflight reserves the body staging capacity, bounded request-plan copies, at most 64 KiB response-header storage, one bounded read buffer, codec scratch, two worst-case encrypted response-part slots (each encoding a 256 KiB raw chunk), a small error-frame slot and status/cancel/completion records. Retained capacities and metadata overhead count, not only payload lengths. All buffers use the same existing connection/device/global counters; no adapter-local pool can evade them. Reserved output count/byte credits are deducted from capacity available to every producer, including ordinary Send. Lease transfer to the mailbox neither allocates nor reacquires credit. Credits recycle only after actual carrier consumption or close.

The initial synthetic adapter uses a 64 KiB maximum read chunk, a checked cumulative 64 MiB body bound, and a separately bounded header count and byte total. MAX_RESPONSE plus one produces Node's 502 before any success part. Truncation, malformed framing and read failure map to the prepaid unavailable result when still deliverable. An implementation must bound transport-library internal buffers and parsing allocations too; configuration assertions alone are insufficient. A maintained, pinned HTTP library and its primary-source behavior must be verified in the later loopback checkpoint. No library selection is made here.

After EOF and successful complete-body validation, the pump encodes one part at a time into the prepaid window. It never constructs a Vec of every encoded frame. Lack of mailbox space pauses delivery while the completion deadline continues. The response body remains raw bytes, with the existing chunk shape/order/headers. If any response part has an unknown delivery outcome, the carrier closes and the remaining parts are discarded; no 502 replacement series, retransmission or HTTP replay follows. With no part delivered, the reserved error path permits a 502/504 if generation/deadline still allow it.

Initially the fixture has no redirects, compression, proxies, TLS or DNS. A later network contract must bound decoded and encoded bytes, verify duplicate-header/URL/status behavior against Node, and authorize redirect targets. Disabling those features is a fixture restriction, not a Node compatibility claim. Allocator/process abort remains outside ordinary typed allocation-failure recovery.

## Cancellation, completion and joined shutdown

Every accepted claim has one prepaid completion slot and cancellation flag owned outside its executor unwind. A coalesced wake plus bounded slot scan lets the worker process terminal results and flush output without incoming commands or caller polling. A completion never allocates an ordinary Approval event or depends on its queue capacity. Executor panic fills a conservative MayHaveRun failure using retained ownership; it cannot detach work or report NotStarted after Begin.

Applied removal/retirement/replacement cancels matching claims and invalidates their epoch before a durable write. Callbacks validate boot, carrier/device generation, claim serial, state and deadline. Stale callbacks can release only their own resources and cannot deliver, reopen a carrier, cancel its successor or restore eligibility. Deadline processing likewise requests cancellation and retains the executor until joined. Cancellation after a side effect remains an unknown execution outcome even if task termination succeeds.

Stop is out of band and Abort remains sticky. Closing joins all claimed executors, drains completion slots, request/output leases and retained status records, then joins the authority worker before terminal persistence. Only that quiescence can support a Clean receipt. Typed terminal failures retain the exact authority/broker/writer guards. Synchronous fsync or an uncooperative executor can delay joining; there is no force-clean or detached-task path. Unexpected unwind inside consuming terminal close keeps the existing documented limitation. There is no persistence of requests for replay and no recovery promise after broker loss.

The reserved eight-control-slot queue can still be filled by duplicate DrainWork; RemoveDevice admission and Disconnect saturation/fairness remain separate P3 gates. An API call refused before removal is applied cannot claim it already revoked work. Dedicated claim cancellation/completion avoids adding that dependency, but does not fix owner control admission. Production integration requires those admission/fairness decisions separately.

## Fixture scope and acceptance tests

The first implementation has no socket constructor, URL, real credential, arbitrary closure or existing-store argument. A later loopback target capability may be minted only by a fresh owned fake server, bound to its exact ephemeral endpoint and synthetic bearer. It may not target an arbitrary localhost port, read proxy/credential environment, follow redirects, import a profile or reach the running daemon. No real phone/relay/provider endpoints are authorized by this proposal.

Required checkpoint tests:

1. Concurrent cloned work tokens produce one winning claim and at most one invocation. Lost enqueue/claim receipts are observed without replay; NotClaimed allows a new attempt, Forgotten does not. Source/device churn, terminal records and executor slots remain bounded. Old-boot and removed/re-paired tokens cannot enter.
2. Deterministic barriers cover cancellation before Begin, after Begin before write, after side effect before result, and during response delivery. Revocation/replacement, stop, executor panic and stale completion never resurrect work; shutdown joins all workers and releases every lease before Clean.
3. Manual clocks cover scheduling expiry, delayed claim, HTTP timeout, 504 during the margin, exact completion expiry and independent idle expiry. A completion with no owner command wakes and delivers. Cancellation/completion still progress with command, approval and advisory queues full.
4. Preflight at needed-minus-one versus exactly-needed connection/device/global bytes invokes zero versus once. Saturate every unreserved pool after Begin and deliver the prepaid error/result. Check mailbox credits, header amplification, chunk boundaries, exact 64 MiB and oversize/truncated streams, fallible allocation and retained-capacity accounting. Partial unknown delivery never becomes a second response or invocation.
5. Retain all existing MemoryHttp and seven Node reciprocal checks. Extend actual Node synthetic fixtures for queue timing, cancellation observations and response bytes; later loopback tests cover real HTTP parsing without contacting a live endpoint. Production routing/credentials, cross-process recovery, actual phones, dense-state census, complete Unicode header/path support, batching and reserved-lane fairness remain excluded.

Requested agreement: the owner-only consuming attempt/status model, claim-based deadlines and separate scheduling bound, preallocated completion/output path, and explicit full-body fixture memory/concurrency limits. Implementation should follow in separately reviewed state-machine then adapter checkpoints. This document does not lift any production gate.
