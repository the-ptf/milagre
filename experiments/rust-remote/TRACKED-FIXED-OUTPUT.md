# Private tracked fixed output

Checkpoint 2 composes the retained two-slot executor with authority-owned synthetic output. Its private operations are `register_fixed_carrier`, `start_fixed_tracked`, `emit_fixed` and `consume_fixed`. `start_fixed` remains independently output-free. No supervisor command, public client API, owner queue, scheduler, automatic emission, HTTP adapter or network transport is added. This implements the [agreed tracked-output contract](TRACKED-OUTPUT-CONTRACT.md), following the separate [reservation/fence checkpoint](TRACKED-OUTPUT-RESERVATIONS.md).

## Admission and ownership

The authority retains at most 16 registered mailboxes. A registration requires an exact Active Registry handle and a fresh, unbound, empty MemoryCarrier. Its immutable identity contains the authority instance, carrier generation and checked target serial. A separate 4,096-byte original-session reservation covers its bounded entry and mailbox bookkeeping until exact carrier close or authority teardown. External MemoryCarrier clones own no worker, receipt or writer capability.

A tracked claim atomically reserves 2,172,416 bytes before the canonical device-key clone, encoding, receipt allocation, worker spawn or Begin. It splits the original connection/device/global charge without releasing or reacquiring counters: 2,101,248 execution bytes, 2,048 metadata bytes, 65,536 scratch bytes, 1,536 packet bytes, and 2,048 grant/receipt bytes. These are accounting allowances, not measured process RSS. A fresh target plus claim adds 2,176,512 bytes beyond existing carrier/request charges. Connection/device defaults remain 64 MiB and the global default remains 256 MiB.

All three fixed Node-compatible 200/502/504 responses are encoded before Begin, with a 999-byte plaintext ceiling. Vector capacity plus explicit codec/crypto/verification headroom must fit the scratch allowance. Inline entry, signal, packet, target and Arc bookkeeping sizes are tested against the fixed allowances. A capacity-one receipt channel is allocated before Begin. Registry and mailbox each reserve one dedicated inline packet slot and 1,024 wire bytes; the ciphertext's lease moves once between owners rather than being charged twice. No VecDeque grows during tracked transfer.

A sole owning grant controls the exact target/claim fence. Both ordinary outbound queues must be empty before admission. Send, send_peer, Finish, MemoryHttp, scoped Claim emission, generic Registry export and ordinary mailbox delivery cannot cross it. Ordinary receive returns no tracked bytes and cannot skip the packet. Busy refusals occur before sealing, fake invocation or export and outside the protocol-close wrapper. Incoming requests, cancellation and other carriers continue. Existing output-free and scoped Claim behavior remains separately tested.

## Delivery evidence and cleanup

`emit_fixed` requires an actual joined Ready result, current authorization and an unexpired retained deadline. It is single-shot. MaySend is recorded under the final session access guard immediately before sealing. The sealed frame enters its dedicated Registry slot, then moves with its one lease into the registered mailbox. Neither queued output nor an observer reading state counts as delivery.

`consume_fixed` retains exclusive authority access, takes the exact session guard, opens the whole ciphertext using the actual synthetic peer Channel, compares it with the selected prevalidated response, destroys the plaintext, and rechecks the retained clock before constructing private PeerAccepted evidence. It returns only fixed-size request-id/status metadata. This is synthetic peer acceptance, not socket or real-phone acknowledgment.

Packet Drop first destroys ciphertext and releases its lease, then publishes private ReturnedCredit through the preallocated capacity-one channel. Only Drop can create this return evidence. Only the verifier can create acceptance. Completed requires the actual joined value, valid peer acceptance, and the actual packet-drop receipt. Merely dropping an unread packet cannot complete work. Receipt processing releases its synchronization before touching Registry/mailbox state. The fence stays held until receipt processing or exact close. Retained completion slots still require explicit disposal; early observation or forgetting an Id cannot free a worker slot.

Before MaySend, cancellation releases unused output grants without inventing a packet-return receipt and retains the execution slot until real join. After MaySend, local seal/transfer/verification failure, cancellation, expiry or unread discard closes the exact Registry carrier and physically drains its mailbox. Existing Removed, Replaced and IdleTimeout reasons survive. Another carrier or successor generation remains usable after a carrier-local failure. Authority-wide clock regression or poison retains the existing sticky Abort behavior and retires all carriers.

Forwarding operations reconcile Registry closure before returning, including malformed receives, exporter timeouts, request completion, dispatch, work draining, private send/export, registration and start refusals. Cleanup does not depend on advisory events or another tick. Delayed receipts after expiry, removal, re-pair, replacement or discard cannot restore Completed or affect successor fences. A missing packet receipt or poisoned mailbox is a dirty cleanup failure.

The session access/epoch lock precedes mailbox locking. Mailbox snapshots release their mutex before acquiring access; verification takes the packet under the mailbox lock and releases that lock before opening it. Receipt publication is nonblocking and calls no authority operation. No epoch, mailbox, receipt or gate lock spans worker join. Explicit close/retire and Drop physically drain registered mailboxes and receipts and join every worker before releasing ownership. Clean/Retired persistence cannot precede those steps. Worker panic, cleanup poison and terminal write failure retain the typed stopped authority and writer guard. Drop never writes Clean.

## Isolated evidence and remaining gates

Sixteen tests added after the reservation checkpoint cover the following, in addition to the existing scoped Claim and fixed executor suites:

1. Original connection, shared-device and global needed-minus-one/exact registration and claim admission; Registry/mailbox byte/slot bounds; occupied queues; direct mailbox and scoped-emitter fence refusal; 16 registered targets and exact closed-slot reuse; pinned bookkeeping sizes.
2. Actual join plus 200/502/504 synthetic peer acceptance with consecutive counters while every remaining budget byte is reserved; ordinary receive/export refusal; one packet lease returned only on actual Drop; no acceptance on unverified drop.
3. Repeated tracked failed-Begin and post-spawn pre-claim rollback; pre-seal cancellation refunds without a receipt or early slot reuse; unread discard, wrong peer, verifier unwinds before/after acceptance, seal failure and transfer failure; retained execution/status evidence and no replay.
4. Delayed receipts across exact completion expiry, removal/re-pair, replacement and discard; unread idle/completion equality; immediate malformed-receive/export-timeout closure; unaffected other carriers and reused numeric carrier IDs.
5. Queued output alongside an unfinished worker during close and Drop; queued clock failure, poisoned mailbox cleanup and typed terminal write failure; physical drainage and actual joins before terminal ownership release.

Validation: 298 Rust tests, 8 doctests, strict all-target Clippy, formatting, example builds and all seven unchanged Node reciprocal/source checks. Every persistent fixture uses a newly created marked synthetic profile and synthetic keys. No production data, host socket, real provider, network, phone build, installed app or push is involved.

Polling still chooses results according to the existing cadence and requires one caller-supplied time base; output retains its start clock for emit/consume and deadline rechecks. No autonomous timeout or completion wake is added. Allocator/process abort, real transport cancellation, batching, production routing and phone interoperability remain outside this checkpoint. The owner queue/fair-pump checkpoint requires separate review and authorization before implementation.
