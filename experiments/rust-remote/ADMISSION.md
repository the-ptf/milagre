# Synthetic authority admission checkpoint

This separately addresses the authority review P2: the former shared 32-attempt/60-second quota let unauthenticated garbage block known phones. Successful reconnects no longer consume failure quotas. Reserved crypto capacity admits known-device candidates even when enrollment failure or crypto budgets are exhausted. The candidate must still authenticate, match its stored kind and pass all consuming service-policy checks before receiving ACCEPT. A clear HELLO public key never grants authorization.

## API and bounds

- `TemporaryAuthority::begin(Source, hello, now_ms, rng)` replaces the old integer source API. `Source::Relay` represents the multiplexed relay, with **no per-phone source/IP visibility**. `Source::Direct(u64)` is only a stable origin assigned by a future trusted direct-carrier adapter, never a peer-provided field. No such adapter is implemented here.
- `policy::Limits::admission` replaces `attempts_global`, `attempts_per_source`, `sources` and `attempt_window_ms`. Failure quotas default to 32 failed unknown-device admissions globally and eight per direct source over 60 seconds. Malformed input, bad token, closed pairing and policy rejection are classified in diagnostic counters. Shape/oversize failures are diagnostic-only and do not spend enrollment failure quota; only failures after crypto admission spend it. Quota rejection itself does not spend another failure. Known-candidate failures have their own diagnostic counter and do not lock enrollment or known reconnects through the long failure quota.
- Pre-crypto admission first bounds HELLO to 105..16,384 bytes and marker 1. Invalid shape spends no crypto units. Valid shape costs `ceil(bytes / 4096)` units (one to four). Independent fixed one-second budgets default to 64 known-candidate units and 16 enrollment units, charged before crypto for both success and failure. Each stored known key has a sub-budget of eight units (`known_key_units`), so spoofing one key cannot consume all 64. `Lane::KnownDevice` reports sub-budget saturation. The per-key table resets with the crypto window and has at most the shared unit limit (hard maximum 1,024) entries, all backed by actual active records. Configured units are capped at 1,024, work windows at 10..1,000 ms. One `&mut TemporaryAuthority` serializes calls, with no internal pre-auth queue. This bounds operation count and input size, not wall-clock CPU/RSS or an external caller's buffered ingress. One service must own one authority; separately constructed authorities do not share these counters.
- The failure source table stores at most 64 IDs by default (configured maximum 4,096). Only failures insert IDs. A full table never evicts entries; additional IDs still charge the global failure quota and increment `untracked_source`. Relay floods allocate no source entries. Window rollover clears the table. Deadlines use checked addition; service time cannot move backwards.
- `admission_status(source, now_ms)` exposes local owner diagnostics: both reset times, enrollment/source lockout flags, failure totals by class, bounded source-table occupancy and remaining units per lane. `PolicyError::Admission` distinguishes `FailureQuota { scope, retry_at_ms }` and `Saturated { lane, retry_at_ms }`. This is a service API, not a new mobile message or implemented owner UI.

A hostile sender who knows a paired public key can spoof that clear routing field and consume that key's sub-budget. Targeting enough distinct known keys can still consume the shared known lane. An authenticated known reconnect may then receive short saturation until the next work window; a sustained targeted flood can repeat this. Claiming unconditional admission for authenticated traffic would require doing unbounded authentication work first. This checkpoint prevents garbage/unknown-key enrollment traffic from spending the known lane or imposing a 60-second known-device lockout. It does not solve targeted saturation, transport fairness or relay edge denial of service. No per-IP mitigation has been implemented at the relay. Carrier ingress bounds, edge admission and fair scheduling still need service design.

## Multi-device window and replay boundaries

`open_pairing(now_ms)` now follows Node's multi-device ten-minute window rather than spending one global enrollment grant. The wire pairing token is unchanged and reusable as Node expects. Two phones and two independently approved desktops can all enroll in the same window. Each ticket remains opaque, instance-bound and consuming. A replacement HELLO invalidates that device's older ticket, a reopened window invalidates old new-device tickets, and deadlines, record changes, removal and retirement still refuse stale callbacks. Desktop approval applies to its exact ticket only. Persistence must finish before release; cryptographic acceptance never means owner approval.

This is ticket/generation replay safety, not a new wire-level HELLO replay cache. Node's existing nonce/key proof and established-channel counters remain unchanged. A valid HELLO can be presented again to start a new authenticated negotiation under the same policy; it cannot resurrect a consumed or replaced callback. Known tickets continue through a window reopen as before. Removed records require `removedAt < pairingOpenedAt`, including same-timestamp denial.

## Evidence and remaining scope

`tests/policy.rs` covers relay garbage/oversized floods followed by valid known admission, independent enrollment/known crypto saturation, explicit known-key spoof saturation/reset, input-byte work charging, 9,996 rejected source-churn IDs with bounded retained state, 1,008 cheap malformed packets followed by successful new enrollment, one spoofed known key saturated while a second remains admissible, exact failure rollover and clock overflow/rollback, 40 successful reconnects without failure charges under a configured larger per-key work budget, multi-device windows, separate desktop approvals and existing ticket/record/persistence guards. The admission/epoch safety checkpoints total 86 Rust tests plus four compile-fail doctests.

`tests/policy-node.mjs` pins TweetNaCl 1.0.3 and runs the exact extracted `openPairing`/`mayPair` source with actual `phoneHello`, `hostAccept` and `phoneFinish`. Synthetic in-memory records establish four new devices in one window, preserve removed-key timestamp behavior, and reconnect a known phone after window expiry. Its committed fixture records source hashes. It does not execute desktop approval/persistence or prove actual phone interoperability. The Rust tests cover those authority decisions independently.

```sh
NODE_PATH=/path/to/trusted/node_modules node experiments/rust-remote/tests/policy-node.mjs
cargo test --offline --locked --manifest-path experiments/rust-remote/Cargo.toml
cargo clippy --offline --locked --manifest-path experiments/rust-remote/Cargo.toml --all-targets -- -D warnings
```

The existing [REGISTRY.md](REGISTRY.md) checkpoint owns synthetic established-session revocation and cancellation. A production driver must serialize authority removal/retirement with registry revocation, schedule `tick`/`expire` during idle, abort external work when its token is cancelled, and route diagnostics to owner UI. None is wired to a listener or live store. Restart recovery, tombstone reclamation, real-frame token census, real LAN/relay lifecycle and phone interoperability remain separate work. Lossless phone bytes and documented strict decoder limits are unchanged.

Pairing-window reopen does not reset cryptographic-failure quotas. Owner code can observe lockout/reset through `admission_status`; there is no UI yet. A valid-shape cryptographic flood can still temporarily block new enrollment. Cheap malformed packets alone cannot create this lockout.
