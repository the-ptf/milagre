# Rust peer/phone protocol checkpoint

`milagre-remote` is a synchronous, in-memory protocol library. It opens no socket, accesses no existing profile or pairing store, and acquires no daemon lock. The synthetic policy model alone creates its own marked temporary record directory. It is not wired into the Rust owner or either app. Mobile source, dependencies and runtime fingerprint are unchanged.

## Session registry checkpoint

`supervisor::Supervisor` now owns a disposable authority and registry on one joined worker, with automatic idle deadlines, bounded queues, composed removal/retirement/replacement and cancellation-safe disposal. It accepts only synthetic identities and in-memory carriers. See [SUPERVISOR.md](SUPERVISOR.md) for commands, receipts, unknown-delivery behavior and service gaps.

`registry::Registry` now owns established sessions, carrier generations, request scheduling and shared leases. Removal, retirement, replacement and idle deadlines revoke operations and cancel queued/in-flight tokens. `tick` processes deadlines without incoming frames; no listener or production timer is started. See [REGISTRY.md](REGISTRY.md) for APIs, Node lifecycle evidence and the stronger in-flight cancellation behavior. Registry persistence/restart and real service integration remain separate.

## Host policy checkpoint

`policy::TemporaryAuthority` owns isolated temporary device records, approval/generation state, multi-device pairing windows, consuming approval tickets, failure-specific enrollment quotas and reserved known-device crypto capacity and shared connection/device budgets. Low-level acceptance now requires a final generation callback and enforces a monotonic age limit. `Channel::open` applies raw token/depth limits before allocating a Value. See [HOST-POLICY.md](HOST-POLICY.md) for source inventory, APIs, evidence and service gaps.

Host challenge/proof codecs, SHA-512 host IDs and Ed25519 signing/verification match synthetic Node fixtures using pinned `ed25519-dalek` 3.0.0. A consuming pending-challenge verifier checks deadline and generation. [HOST-PROOF.md](HOST-PROOF.md) records primary sources, actual signature reciprocity and deliberate weak-key rejection differences.

## Phone assembly checkpoint

The `phone` module now supplies request/response body codecs, bounded host upload assembly, and ordered phone-side response/live/batch dispatch. `Channel::open_encoded` exposes authenticated bytes for the owner's lossless `jsjson` boundary; `JsText` preserves live-data string tokens without PUA substitution. See [PHONE-PROTOCOL.md](PHONE-PROTOCOL.md) for APIs, local deadlines/cancellation semantics, stricter admission limits, remaining Unicode restrictions, and the host-proof/LAN/relay lifecycle inventory. This remains an in-memory library; HTTP forwarding, network lifecycle, owner approval/persistence services and actual phone interoperability are unimplemented. A consuming authorization gate is now required by the crypto API; see [SAFETY.md](SAFETY.md).

## Public API

- `channel::phone_hello(phone, host, token, options, rng) -> (bytes, PendingHello)`, `PendingHello::finish(reply) -> Channel`, and `channel::host_accept(host, hello, token, is_known, can_pair, rng) -> Accepted`. Use a cryptographic RNG such as `rand_core::OsRng`; deterministic RNGs exist only in fixture code. The pending hello is consumed by finish, and channels expose neither cloning nor key bytes.
- `Accepted` keeps reply/channel/device private. Inspect `device()` and consume `authorize(ServiceDecision, still_current)` with a last authoritative generation callback after the service has checked current identity/generation, stored kind, desktop access, owner approval and completed pairing persistence. Only successful authorization returns `Authorized { reply, device, channel }`. Decisions have no permissive default; a refusal consumes the acceptance. Callbacks `is_known` and `can_pair` must be read-only: Node and Rust call `can_pair` even for known devices.
- `Channel::seal_encoded(&[u8]) -> Vec<u8>` preserves serialized JSON bytes; `Channel::open(&[u8]) -> serde_json::Value` authenticates, checks sequence, validates bounded raw JSON, and parses JSON. Domain request schemas and dispatch remain the caller's responsibility. Authenticated invalid JSON consumes its counter, exactly as Node does. On protocol errors a service should close the connection, as Node does.
- `peer::{FrameWriter, FrameReader}` take `Direction::{Rpc,Evt}` and accept shared `ConnectionBudget` handles through `with_budget`. Writer returns leased `EncodedFrames`; `read(encoded, now_ms)` returns `Option<RawFrame>` with `as_bytes()`. Both validate raw JSON without building a `Value` tree. Reader exposes `deadline_ms` and `expire`; callers must schedule expiry even when idle. Batch dispatch must feed each item in order. No daemon RPC or TCP stream dispatch is provided.
- `envelope::{Envelope,Kind}` encodes/decodes the relay's borrowed payload and full `u64` connection ID. The envelope supports OPEN/DATA/CLOSE and HOOK/HOOK_SET/HOOK_ACK/HOOK_RESULT tags; webhook contents and service behavior are not implemented.

## Exact wire contract

| Layer            | Bytes or shape                                                                                                                                                                                                                |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Relay envelope   | Concatenate `type:u8`, `connection:u64 big endian`, `payload`. Device connections are nonzero; hook messages use zero.                                                                                                        |
| HELLO            | Concatenate `01`, client ephemeral public key (32 bytes), persistent public key (32), nonce (24), and NaCl box of `{token,eph,name?,kind?,caps?}`. Authenticated `eph` binds the clear key.                                   |
| ACCEPT           | Concatenate `02`, host ephemeral public key (32 bytes), nonce (24), and NaCl box of `{eph,peer}`. Both ephemeral keys are bound.                                                                                              |
| Channel DATA     | Concatenate `03`, counter (u64 big endian), and secretbox of JSON. NaCl tag precedes ciphertext; counters start at 1 in each direction.                                                                                       |
| Channel nonce    | 24 bytes: direction at offset 0 (client to host 1, host to client 2), zero at offsets 1 through 15, counter big endian at offsets 16 through 23.                                                                              |
| Desktop frame    | `{"t":"rpc","frame":<raw JSON>}` or the corresponding `evt` message, through 768 KiB of frame JSON inclusive.                                                                                                                 |
| Desktop fragment | Above that threshold: consecutive `{"t":"part","id":N,"i":I,"n":COUNT,"data":"<padded base64>"}` with 512 KiB raw pieces, increasing per-writer IDs starting at 1, and zero-based indices. UTF-8 codepoints may cross pieces. |

The session cipher is RustCrypto `SalsaBox::new(peer_ephemeral, own_ephemeral_secret)`. It performs the same X25519 and HSalsa20 precomputation as TweetNaCl `box.before` and then the same XSalsa20-Poly1305 operation as `secretbox`. This crate implements only framing and validation around those library primitives. It implements no cipher, MAC, KDF or elliptic-curve arithmetic.

Primary-source verification, checked 2026-11-10:

- [RustCrypto NaCl compatibility repository](https://github.com/RustCrypto/nacl-compat) maintains the selected crates.
- [`crypto_box` 0.9.1 source and API](https://docs.rs/crypto_box/0.9.1/src/crypto_box/lib.rs.html) specifies `SalsaBox`, X25519 shared-secret derivation, 24-byte nonces and the secretbox delegation. The published source was also inspected locally after Cargo resolution.
- [`crypto_secretbox` 0.1.1 source](https://docs.rs/crypto_secretbox/0.1.1/src/crypto_secretbox/lib.rs.html) implements the NaCl-compatible XSalsa20-Poly1305 box, including its tag layout. The dependency is brought in by `crypto_box`, rather than duplicating its precomputation here.

`Cargo.lock` pins the resolved dependencies. No claim is made that this integration has received a security audit.

## Bounds and deliberate stricter parsing

The relay carrier is limited to 1 MiB payload plus its 9-byte multiplex header, from `apps/relay/src/room.mjs`. A channel plaintext is therefore at most 1 MiB minus 25 bytes (9 header + 16 tag). This library applies that bound on every channel, including a future LAN integration. A hello/accept has an additional local 16 KiB admission bound. Existing generated hellos are far smaller; the Node crypto helper itself has no such bound.

A desktop frame is at most 16 MiB, at most 32 fragments, with one incomplete frame per reader. Streaming/raw validation caps depth at 64 and lexical tokens at 65,536; it does not materialize strings, arrays or maps. Each reader error drops its partial buffers. Shared per-connection and global reservations cover retained pieces, final contiguous copies, output frames and fixed metadata/scratch allowances, including completed frames until the caller drops them. Default constructors share a process-wide 256 MiB global pool and use separate 64 MiB connection handles; services should explicitly create one global pool and one connection handle shared by both directions and writers. Incomplete frames expire 15 seconds after their first piece by default; a service must poll/schedule `expire`, not rely only on new messages. See SAFETY.md for exactly what is charged and remaining owner/parser/socket budgets.

The recorded emitted Node messages are byte compatible. Admission limits also reject some valid Node JSON; this is not universal Node-payload compatibility:

- Peer envelopes reject unknown fields, missing fields, duplicate recognized fields and unknown tags. IDs must fit JavaScript's safe integer range; fractional/negative unsigned fields are rejected. Node readers are more permissive with extra or missing fields.
- Base64 must be canonical, with correct padding and zero trailing bits; a decoded fragment may not exceed 512 KiB. Node's permissive decoder accepts some noncanonical spellings and the maximum encoded length can represent one extra byte.
- Peer JSON must be valid UTF-8, satisfy the 64-depth/65,536-token admission scan and pass raw JSON grammar validation. Raw frame strings preserve lone surrogates and PUA; numeric lexemes are not converted. `Channel::open` and handshake typed fields remain ordinary serde decoders; `open_encoded` avoids that lossy boundary. Peer envelope tags and base64 strings must be unescaped JSON strings. Owner parsing and domain schemas remain separate.
- Known hello/accept fields cannot be duplicated. Unknown hello/accept extension fields remain allowed, matching old-client extensibility. Hello names and capabilities retain Node's sanitization/filtering rather than rejecting old optional metadata. Authentication errors preserve `bad-hello`, `bad-token`, `unknown-phone` and token-before-kind precedence for recorded cases.
- Unknown relay envelope tags and hook/device connection-ID misuse are rejected, whereas Node often ignores them. Counter/fragment-ID exhaustion returns an error instead of wrapping or becoming imprecise.

These differences are documented admission hardening, not a mobile wire change. If real-client testing finds valid traffic outside these limits, review the contract before integrating; do not silently relax it.

## Reproduce checks

From the repository root:

```sh
cargo test --manifest-path experiments/rust-remote/Cargo.toml --locked
cargo clippy --manifest-path experiments/rust-remote/Cargo.toml --all-targets --locked -- -D warnings
cargo fmt --manifest-path experiments/rust-remote/Cargo.toml --check
cargo build --manifest-path experiments/rust-remote/Cargo.toml --example conformance --locked
node experiments/rust-remote/tests/node-fixtures.mjs experiments/rust-remote/target/debug/examples/conformance
```

If this worktree has no Node dependencies, set `NODE_PATH` to an existing trusted installation's `node_modules` for the last command. Only `tweetnacl` is loaded from it; the script asserts the repository-pinned version 1.0.3 before importing protocol code. Protocol source is always read from this worktree. Fixture generation resolves the existing TweetNaCl import, imports the real shared modules and extracts the exact pure `frame` function from `phone-channels.cjs`; it never imports the service dependency graph or calls startup. No network connection is needed for tests after Cargo dependencies are available.

`node experiments/rust-remote/tests/node-fixtures.mjs --record` regenerates committed **synthetic** fixtures. This is an explicit update command; normal verification compares current Node outputs and source hashes to the committed fixtures first. Review any changed production contract before recording again. All keys and messages in `tests/fixtures/node.json` are public test material.
