# Isolated Claude owner bridge

`ClaudeFixture::create(Scenario)` implements the nonblocking owner Provider contract over `milagre_claude::ClaudeSession`. It creates a fresh private Project/profile and launches only the fixed Cargo sibling `runtime-fake-claude`, compiled directly from the checked-in rust-claude fixture source. It accepts no executable, external path, credentials, environment, role or MCP endpoint. `claude-runtime` exposes this fixture through the existing owner actor and a separate private wire profile. It cannot connect to the installed app or production daemon.

Each Chat has a private executor and one Claude session, bounded to 16 workers, one queued start, eight queued answers, 32 outstanding answer receipts globally and 256 ordinary events/4 MiB serialized payload plus bounded terminal/answer reserves. Completed slots are removed on subsequent admission. Provider methods only enqueue; synchronous Claude answer callbacks run on the worker. Close is bound to the captured slot and current host TurnId. Closing slots refuse new turns until fully stopped. A stale close cannot stop its replacement. Overlapping starts and implicit extra turns are refused; production steering is still gated.

Each admitted turn receives Started or StartFailed. A running turn emits one host terminal, then one generation-bound Exited when its session closes. Compact subagent settlement deltas from close are forwarded before the terminal/exit without replacing transcript history. The owner merges transcript rows by id. Normal shutdown and cancelled startup retain the executor, profile and worker permit until all supervisors finish reaping. A three-second deadline latches cleanup failure and closes admission; it never releases an unreaped child. The fixture executable reports `CLAUDE_CLEANUP_INCOMPLETE`, waits for cleanup, and exits with failure if that deadline was exceeded.

Permission/question replies use the owner's asynchronous AnswerId contract. Accepted means the Claude callback resolved, not that its transport write or tool execution completed. NotWaiting means no callback waited. A queued answer dropped before entry may fail; cancellation after callback entry is Uncertain. The delayed-receipt fixture proves the CLI received the answer before cancellation, and requires Uncertain rather than rollback. Actor replies wait for the matching owner notice and publication. The owner's unresolved-answer cross-turn lifetime contract is still under review; this adapter does not evict or replay those slots.

RawJson provider events enter the owner codec once. Outbound prompt/answer text preserves literal noncharacters and private-use characters, replacing lone UTF-16 units with U+FFFD only in the native CLI copy. Stored originals remain lossless. Request/question identities, keys and model/resume metadata stay strict. Ordinary Ask mode and text-only model/effort/initial-resume settings are admitted. Images, fast/TLDR/ultracode, reply assembly, roles, arbitrary launch configuration and MCP are refused. Initial resume is checked on the actual fake process argv; a reused session refuses a different native identity until closed.

## Evidence

Eight `claude_bridge` integration tests use the fixed native fake process. They cover sequential turns/process reuse, permission/question receipts, Stop, crash, cancelled initialization, refused policy/image configuration, cancellation after callback delivery, stale close, initial resume and conflicting identity refusal, drop/reaping, and compact subagent transcript retention through the real owner reducer.

The production Node daemon client and desktop runtime client run six fresh fixture scenarios: reply/text, permission, question, Stop, crash and Unicode. Both prompt and question-answer Unicode frames are asserted inside the fake CLI. Marker/PUA output survives the provider-to-owner boundary once; saved prompt text retains its original lone surrogate. Every fixture verifies both temporary profiles disappear after successful shutdown.

This checkpoint does not replace the shared Node runtime, prove real-provider compatibility, wire account/tool policy, or install any app. Native MCP sharing, queued-turn coverage and broader session/resume lifecycle coverage remain follow-up work.
