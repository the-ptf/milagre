# Proposal: production UI with a fresh Rust-only fixture owner

Status: planning only. No API changes, launch, installation, live-profile adoption or ownership cutover is included. Source inspected on the local migration branch after `457f176d`, `0dbbdff7` and `b4c248c3`. The historical paragraphs in [BACKEND-MIGRATION.md](../rust-desktop/BACKEND-MIGRATION.md) describe earlier checkpoints; the current source and its explicit gates govern this proposal.

## Decision

The next smallest meaningful integration is an **owner-backed workspace bootstrap service** for one generated Project, followed by a separate development app route. It should make the existing production React UI discover that Project, select a truthful scripted model, display existing Chats and runs, and send/cancel/queue text through the Rust owner. It must then expose the existing shared content owner so the same window can display and edit a Design and Artifact.

This is more useful than another transport test: current clients already prove socket/paging, streaming, persistence and content contracts separately. The app has not been driven through those Rust services together. The first deliverable is the missing startup contract, not removal of the provider or handover safety gates.

The route uses the production React source, production preload API, Tauri bridge and real WKWebView. It does not replace the UI with a fixture screen. A distinct development bundle name/icon and a clearly marked fixture title identify synthetic data and provider output. Any screenshots from this route are test evidence, not production-provider or PR screenshots.

## Startup commands to integrate first

The production preload names below are concrete dispatch gaps, not invented endpoints. `App.tsx::loadInitialProject` calls `getCurrentProject`; project reload uses `readProject`; the model selector uses `getModels/getCliStatus`; `useAgentRuns` uses `getRuns`; sidebar/settings read recent/known/registered Projects and Links. The final required call set must be recorded from the real fixture WKWebView before claiming startup coverage.

| Command                                                                                               | Existing implementation to reuse                                                    | Required behavior and authority                                                                                                                                                                                                                                                                     |
| ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `project:current`, `project:open`, `project:switch`                                                   | Actor supports these today                                                          | Trusted startup opens the generated Project before first snapshot. `current` never retries failed recovery. Normal calls select only that canonical admitted Project; no folder picker or arbitrary path adoption                                                                                   |
| `project:read`                                                                                        | ReadHandler supports a read path; actor lacks the command                           | Add an actor-backed read matching Node's `{state:false}` and full-state result, version/epoch and read-only readiness behavior. Do not open a second `ProjectStates` or silently reopen a forgotten Project                                                                                         |
| `chat:runs`                                                                                           | `ChatHost::runs` and actor snapshot already exist                                   | Return the same owner run snapshot/sequence used by publication. Do not reconstruct an independent run cache                                                                                                                                                                                        |
| `project:recent`, `project:known`, `project:registry`, `link:list`, `canvas:snapshot`, `canvas:links` | `rust-registry` saved snapshot/identity grants and fresh `RegistryCopy` writer      | Seed only the generated Project and an explicitly empty Link set. Map real Node result shapes, ordering and errors. A registry row is metadata, never a grant to open an arbitrary path. Begin with reads; defer registry/Link mutations                                                            |
| `agent:models`, `agent:cli-status`, `accounts:list`, `accounts:scope`, `accounts:scopes`              | Pure `rust-accounts::Accounts`/`Selection` plus a new fixed fixture catalog adapter | Advertise only the scripted provider/model and synthetic scope. Do not probe CLI binaries, credentials or HOME. Record exact Node-compatible shapes and prove the production model selector can choose it; do not label a real account logged in. Use the fixture title to make simulation explicit |
| `usage:cached`, `usage:accounts:cached`, `usage:read`, `usage:accounts:read`                          | `rust-usage` has account-scoped cache/service boundaries, currently unwired         | First route may truthfully report unavailable synthetic quota using the existing production shape, with no quota transport. Do not invent zero usage or a successful real-account refresh. A limits-bar sample is visibly synthetic, not a performance or billing observation                       |
| `chat:inbox`, `designs:enabled:read`, `designs:enabled:save`                                          | Present in ReadHandler, absent from the actor                                       | Compose inbox reads from the same ready owner state; keep the ordinary inbox distinct from the permitted floating-inbox omission. Add Design enablement using fixture-owned settings before expecting the Design UI to appear. Do not call the separate read handler over actor data                |
| `chats:home`, `chats:ensure`                                                                          | No actor route                                                                      | Defer home creation in the first single-Project route. The sidebar new-Chat-without-Project action must report unsupported, not return a live home. A later generated home needs its own explicitly admitted owner scope                                                                            |

`project:open-at`, `canvas:open-project`, onboarding clone/init, `fs:list-dirs` and global folder picking remain refused until their admission contract is implemented. The next patch should not broaden the existing method allowlist speculatively. A command may return a truthful empty collection only when the generated fixture actually owns that empty collection; unsupported operations retain structured errors.

Other immediate UI gaps include `chat:patch`, `chat:delete`, `chat:resume`, `chat:reload`, `chat:limit-switch`, limit-resume scheduling, `agent:set-permission-mode`, `agent:dismiss-suggestion`, task output and advisor commands. `chat:send` supports owner-created sessions, but the app's new-Chat/worktree flow and full send shape must be verified before enabling those entry points. These are not solved by listing models.

The production send object includes model/effort, permission mode, `images/files`, fast mode, replies and TLDR settings. Fixture defaults must produce the existing admitted text-only configuration, and unsupported options must remain explicit. Do not strip meaningful request fields in the bridge to make the test pass.

## Proposed Rust daemon + WKWebView route

All names in this section are proposed interfaces, not existing APIs.

1. **Fresh daemon composition.** Add a feature-gated `app-fixture` executable and private `app_fixture::start()` constructor. It accepts no profile path, repository path, executable, account, environment or network address. It creates a fresh `IsolatedProfile`/`Isolation`, generates one Project, opens it through `ChatHost::open_project`, attaches a single shared content owner and a fixed scripted provider, and binds one Rust wire server. Keep default handover/steering gates. Use a scripted resumable session for repeated ordinary turns, not ACP's nonresumable fixture and not a fake restoration bypass. Registry and content directories live under this same authority. Do not compose `start_owned()` beside it.
2. **Private bootstrap handoff.** A Rust development launcher starts only fixed bundled sibling binaries. The daemon supplies endpoint/profile identity over inherited private pipes; the launcher passes a typed, fixture-only launch context to the shell. The shell must verify the created directory/socket identity, owner UID/mode, expected child PID and bootstrap version. Reconnect uses only this pinned endpoint. There is no caller-selected production profile, no production fallback and no global `MILAGRE_DATA_DIR` override. Dropping the launch pipe cannot silently connect the installed Node host. Existing `ProfileLease` protects local owners; cross-process cleanup must wait for both joined daemon work and the child window's storage release.
3. **Explicit shell storage and action context.** A fixture-only `LaunchContext` would carry endpoint authority and generated roots for preferences, WebKit data/localStorage/outbox, window state, instance lock and smoke output. `Preferences`, transport construction, native path resolution and lifecycle acquisition must receive that context instead of reading the installed paths. This requires coordinated desktop edits later, not a HOME rewrite. No live preference inheritance, production desktop registration, remote-computer unlock, notifications, keep-awake subprocess or restart-host action is permitted from this route. Any fixture `desktop:register` support must target only this owner and its private preferences. The ordinary installed app retains its existing context and process.
4. **One production renderer.** Reuse current Vite aliases and preload shim. No mock IPC shim answers domain calls: bootstrap/catalog reads, sends, history, snapshots, events and Artifact operations cross the real Rust socket. The shell must identify the fixture host without falsely advertising `computer-management-v1` or `state-patches-v1`; agree a fixture launch marker and an explicit outdated-host UI policy first. Unsupported Browser/voice/floating inbox remain the user's permitted omissions, while other absent actions are recorded as fixture limitations. Seed one small Design and HTML Artifact through the same owned native stores, and package the fixed `milagre-design-raster` helper for this development bundle only.
5. **Evidence and teardown.** Drive the real WKWebView: initial sidebar/current Project/model, text send/stream/Stop, queued successor, permission/question cards supported by the scripted owner, reconnect, transcript reload, Artifact preview, Design edit and PNG/export path. Verify saved messages/revisions from the private owner and compare actual rendered screenshots with the existing app's design. Test malformed endpoint, ownership loss and shell/daemon exit without any fallback. Require `QuitState::Done`, joined provider/transcript/content workers, closed socket and released profile before reporting graceful completion. Pending quit keeps the fixture reachable for retry. A forced teardown is reported as a crash boundary. Record every owned process; Rust-owned fixed fakes/helper processes are allowed, a Milagre Node daemon or SDK sidecar is not. Build-time Node is excluded from runtime measurements and stated separately.

The launcher/context and bootstrap command schemas require parent/desktop/owner agreement before implementation. The current shell has no ready fixture endpoint API and no local-auth handshake implementation; enabling wire authentication requires an explicit client handshake rather than claiming the existing production transport already supports it. For a same-user private Unix fixture, preserve the wire's current unauthenticated-local mode plus OS/private-pipe authority unless that contract is deliberately changed.

The first route should use no network listener, remote service, credential store or existing Project. A real PTY is not an OS sandbox; do not expose arbitrary shell input in the first app fixture merely because terminal unit tests pass. Integrating `TerminalService`/ports into the actor is a subsequent service slice with a trusted Chat resolver, event forwarding and joined disposal. Git/Worktree actions likewise need their actual owner grants, not the current private-repository mapping.

Terminal, accounts, Designs/Artifacts, core Chat features and existing-data compatibility remain migration work, not implied omissions. No performance win or completion claim follows from this proposal. The eventual comparison must include all owner/helper/provider processes and distinguish scripted UI evidence from real-provider measurements.

## Proposed acceptance checkpoint

Approve and implement only the fresh-profile bootstrap/catalog service and typed development launch context first. Compare every added daemon response with the real Node implementation on equivalent generated state. Then run one real WKWebView session through the separate Rust-only fixture route, enumerate every unsupported method encountered, and demonstrate normal send/queue/Stop plus Design/Artifact round trips. Keep the installed `~/Applications/Milagre Rust.app` and the production Node daemon untouched until a separately validated installation decision. Production adoption remains a later capability and lifecycle project.
