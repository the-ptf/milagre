# Rust backend migration: actual status and remaining work

This branch is a Rust desktop-shell migration, not a completed Rust backend migration. The shipped React renderer is reused, and the Rust client connects to the installed Node daemon. The daemon still owns all agent execution and persisted Project/Chat state. Removing Electron from the window does not remove Node from Milagre's backend.

The installed Electron app and this client share the daemon through its existing private socket. They must never create concurrent writers for the same Project. This preserves ADR-0003, the SQLite/JSON stores and existing desktop/mobile event contracts. The Rust app currently depends on that daemon already being available. It is not yet a standalone replacement installer.

## What has moved

| Layer                                                                                                               | Current implementation                                                             | Remaining dependency                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |

| Daemon client transport                                                                                             | Rust: `src/transport.rs`                                                           | Node daemon server at the existing profile socket                                                                          |
| Artifact/media local scheme serving                                                                                 | Rust: `src/content.rs`                                                             | Node artifact stores, provider commands and generated-content assets                                                       |

| App UI, sidebar items/filtering/limits, Chat, Changes, Designs, Artifacts                                           | Existing React/TypeScript renderer and production preload API with a Tauri adapter | Shared TypeScript models and rendering libraries, intentionally retained                                                   |

The optional floating inbox, browser embedding, voice and visual effects can remain unavailable for this experiment. That allowance does not extend to losing Chat sending, permissions/questions, Worktrees, Designs, Artifacts, terminal sessions, settings, accounts or existing data.

## Execution stages and acceptance gates

1. **Desktop parity while retaining the owner daemon.** Finish the production renderer adapter and native shell commands, then exercise sidebar filtering/limits, Chat streaming/send/cancel/permissions/questions, attachments, Changes, Worktrees, terminals, Designs, Artifacts, accounts/settings and phone synchronization. Record supported, intentionally omitted and broken states separately. Do not equate a boot smoke test with parity. The existing Electron UI remains the comparison reference.
2. **Rust service foundations, initially read-only.** Implement runtime command schemas, structured errors, event sequencing, storage readers and process supervision. Compare Rust reads against Node outputs on fixture copies and live read-only samples. Establish Unix and Windows ownership/authentication behavior before permitting a Rust process to own existing user data. Keep schema migrations backward compatible until rollback is proven.
3. **Move the single owner in controlled domains.** Port stateless/read-heavy services first (usage parsing, catalog discovery, Git reads, content reads). Port persisted Project/Chat state, Worktree mutations, terminal ownership and content mutations behind explicit ownership boundaries. A temporary Node-to-Rust service RPC is acceptable, but each domain must have one writer and the inventory must list all remaining Node processes. Never allow two independent hosts to write the same Project for comparison.
4. **Move orchestration and remote connectivity.** Port provider adapters, Chat state machines, MCP/tool dispatch, routines/delegations, account flows and relay/peer/mobile services. Run protocol fixture tests and real provider exercises for resume, limits, cancellation, approvals and disconnected clients. Provider executables may themselves use runtimes outside Milagre; distinguish external provider processes from a retained Milagre-owned Node daemon or sidecar.
5. **Standalone replacement and upgrade qualification.** Package and launch the Rust owner without installed Electron/Node services; preserve data-directory discovery, active-turn shutdown, upgrade/rollback and shell integration. Test an Electron installation upgrading to Rust with existing Projects, linked Worktrees, Chats, accounts, preferences, Designs, Artifacts and paired phones. Measure cold/warm startup, full process-tree footprint, idle CPU, transcript scrolling, streaming latency and terminal throughput on equivalent data/features. Only then call the backend migration complete or propose replacing the main installer.

GPUI remains a separate rendering experiment. It would require porting React components, layout, text selection, accessibility, input, Markdown/code, canvas and embedded content. It is not necessary to make the backend Rust and should not be introduced into the same compatibility cutover without its own parity evidence.

## Completion definition

The migration is complete when the production feature set retained by the user runs through the Rust owner, the installed Electron application and Milagre-owned Node daemon/SDK sidecars are no longer required, existing data and paired clients survive an upgrade/rollback test, and equivalent-workload performance measurements include every owned process. At the current stage, those conditions are **not met**.

## Native follow-up status

Rust now forwards `app:set-keep-awake` to the existing daemon owner, so it changes the existing blocker instead of creating another `caffeinate` process. Keybindings JSON opens through the daemon-reported path. Linear OAuth uses the daemon's existing system-browser flow; Electron's dedicated OAuth window is not reused. These user-facing launches remain suppressed in background mode.

The Rust notification port uses `tauri-plugin-notification` 2.8.1. It handles waiting/completion events, background-work deferral, custom chimes, focus/hidden filters, a timezone-aware schedule, unread Dock counts and click-to-open Chat. Model/schedule tests run without sending notifications. Real system delivery and click behavior have not been exercised during background smoke checks. The plugin cannot retract delivered macOS notices after requests resolve; notification previews currently compact plain text rather than applying all production Markdown cleanup. See the [official plugin API](https://docs.rs/tauri-plugin-notification/2.8.1/tauri_plugin_notification/struct.Notification.html).

A separate migration blocker remains in `apps/desktop/electron/computer-unlock.cjs`: paired-computer credentials are sealed with Electron `safeStorage`, and the desktop unlocks the daemon's vault. An already-unlocked owner continues serving this Rust client, but a standalone Rust replacement must migrate/unlock that wrapper through the OS keychain before paired-computer startup and Add Computer have parity. Do not replace a missing wrapper with a new master key, read secrets into logs, or present an unlocked development daemon as proof this migration is complete.
