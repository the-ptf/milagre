# Copied registry writer contract

Implemented copied-store contract grounded in `packages/core/src/project-registry.cjs`, `recent-projects.cjs`, `project-groups.cjs` and `project-links.cjs`. The contract was committed separately before the writer. The implementation and its tests are confined to `rust-registry`; the production owner remains Node.

## Ownership and admission

The writer accepts a fresh copy capability created inside an existing `Isolation`, never an arbitrary profile path or an adopted existing store. Creation requires a new private directory, pins its descriptor and identity, and records a random copy marker. Seeds are bounded supplied JSON bytes, not source paths. Projects referenced by seeds must still pass the existing isolated identity/admission boundary before any operation treats them as Projects. Fresh registry registration takes an explicitly verified in-copy identity, never trust renderer-provided `{id,path}` records.

One writer holds an advisory `flock` on both the pinned directory and a private lock file. The directory lock prevents a replaced lock pathname from admitting a second writer. Each write checkpoint verifies copy marker, directory identity, held lock-file identity/token and owner callback. File opens and renames are descriptor-relative with no symlink following. No PID-based takeover, lock deletion or live-profile adoption is allowed. OS release after process exit permits normal fresh acquisition; it is not a forced lock takeover. A retained copy capability can reacquire after a clean close or a crashed worker, with disk reread before mutation.

A writer serializes operations in Node call order. The public API must retain ownership across asynchronous identity discovery and must not allow a dropped future to release the single-writer guard midway through a write. No runtime wire endpoint is added by this work.

## Exact Node registry operations

`read()` returns a normalized top-level object. Invalid/missing JSON or a non-array `projects` field becomes `{scanned:false,projects:[],links:[],worktreePositions:{}}`. A valid file becomes, in this property order, `scanned`, `projects`, `links`, `projectGroups`, `worktreePositions`. Project rows keep unknown fields but retain only absolute string id/path and the first row for each id. Links are kept as the saved array. Groups are filtered by `validProjectGroup`. Positions retain any truthy JavaScript object, including arrays. Unknown top-level fields are dropped by Node; they must not be invented or preserved in Rust writes.

There is no Project-delete method in Node `createProjectRegistry`; this work will not invent one. Removing a Project from the recent menu is `recent.forget`. Persisted Project removal happens through Node's stale-entry cleanup. `list()` also scans default discovery roots on its first call; production discovery is excluded here. A bounded explicit copied-root scan, if added later, needs its own contract.

## Presence and uncertain identity

`Registry::probe` returns present (`Some(identity)`), definitely gone (`None`) or unverifiable (`Err`). A missing/non-directory path component strictly within the isolation, without a preceding symlink or I/O error, proves absence. A successful identity that differs from the saved id/main path may be removed by general update as Node does. Capacity, subprocess timeout, unsupported includes/redirection, Git inspection limits, permission failures and changed ownership never count as absence. Every general update, registration cleanup and active-Worktree catalog propagates those failures and commits nothing. This intentionally refuses work that Node might prune after a weaker identity check.

Discovery within a mutation has a 30-second timeout. A discovery future can be cancelled without starting a later write; any already-running bounded read worker finishes without mutation. Final staging/sync/rename has no await and is not preempted by that discovery timeout. This library has no background mutation actor, ticket endpoint or retry. A future runtime owner must retain the returned commit outcome rather than fire-and-forget calls.

## Recent Projects

The saved list normalizes each row to exactly `{path,name,openedAt}`. Paths use Node lexical `path.resolve`, not realpath. The first duplicate normalized path wins before filesystem filtering; missing/non-directory paths drop; at most ten remain. Unknown row fields are dropped. Missing/corrupt JSON reads empty; mutation reads propagate other I/O errors rather than wiping the list.

`add(path)` requires an absolute path. If it is already the first retained path, return the same list without a write or changed `openedAt`. Node still invokes its injected clock before validation/read, including invalid and no-op calls; Rust preserves that order. Otherwise prepend its normalized path, basename and injected ISO time; remove older occurrences; cap to ten; write. `forget(path)` normalizes an absolute target, filters it out and always writes the normalized current list, even if nothing matched. It never removes a folder. Rust requires an explicit verified in-copy root for selection/addition; stale/unavailable recent entries may still be forgotten. Launch and renderer `switchTarget` behavior are separate and are not authorized by a generic path.

## Persistence and failure contract

Node creates the parent directory, writes the entire `JSON.stringify(value, null, 2)` bytes to a process/counter temp file, then renames it over the target. No trailing newline is added. On write/rename failure it removes the temp and propagates the error; the prior target stays intact. It does not fsync or journal the two independent files. Registry and recent-list writes are independent transactions, never represented as a single atomic update.

The copied Rust writer preserves Node JSON key ordering, numbers and lone UTF-16 escapes through `jsjson`, including two-space formatting. It uses private 0600 files, unique `create_new` staging, file sync before rename and parent-directory sync after rename. The durability additions must not change successful bytes or operation results. A failure before rename leaves the old file unchanged. A failure after rename is reported as committed-but-durability-uncertain and must never invite automatic replay. Ownership loss must be detected before every staging/rename checkpoint, with no cleanup through a replaced path. This checkpoint never removes crash leftovers at restart. Only the current operation can clean up its exact staging name, and only while ownership still verifies. Retained capabilities support a fresh writer after a worker process exits; loss of all capabilities does not authorize adopting an old profile.

Implemented checks:

1. Actual Node writer traces compare each result and both saved files after every supported operation, including no-op ordering, unknown-field handling, invalid mutations, member reordering, stale entries, restoration, recent dedup/cap and restart.
2. Same-process and second-process exclusion; replacing/removing the lock or directory must refuse writes and preserve outside sentinel bytes. Failed release must not delete another owner's lock.
3. Inject failures before staging, before rename and after rename; distinguish unchanged versus committed/uncertain bytes. An invalid mutation never persists prerequisite cleanup.
4. Restart after clean close and process interruption; only complete old or new JSON is accepted. Pending stages cannot be mistaken for committed data, and cleanup cannot touch unrelated files.
5. Every write stays in the fresh copied-store capability. No live registries, host restart, lock stealing, Git mutation or native mobile changes.
